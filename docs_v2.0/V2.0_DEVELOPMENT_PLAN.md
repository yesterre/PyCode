# PyCode v2 开发计划

## Repository Source 补充约定（2026-09-09）

v2 的主要入口是 Git Repository URL：用户创建 Project → index 请求获取仓库到受控 Workspace → Core 建立 Index / Code Graph → ready → 后续分析。统一使用 `repo_url`，不绑定 GitHub。

Project 是业务元数据，不等同于源码目录。Phase 2 对外创建字段为 `name`、`repo_url`、可选 `branch`，响应包含 `status`；客户端不提交 `local_path`。创建只登记，不 Clone；允许同仓库创建多个 Project。内存 Store 暂存元数据，Workspace 按 Project UUID 隔离，服务器绝对路径不作为外部 Project 契约。

Phase 2 补充基本 HTTPS Clone 与 Workspace 准备：首次 index 执行 Clone → Index → Graph；已有仓库时复用当前工作区，不自动 pull。状态为 created → preparing → indexing → ready，失败进入 failed 并提供安全错误。保持 Router → Service → Adapter → Core 分层，不修改无关 Core。

仅允许配置的公共 Git Host、无内嵌认证的 HTTPS URL。Git 使用参数列表、关闭交互并设置超时；不递归获取子模块，不安装依赖、不运行仓库程序或测试。准备和分析前验证受控目录及链接边界。

Phase 3 负责 PostgreSQL 元数据持久化，源码仍在文件系统。Phase 4 在基本 Clone 上增加远程更新、Commit / Snapshot 一致性和历史生命周期。当前不引入 PostgreSQL、ProjectSnapshot、Redis、Worker 或 SSE；后文 Phase 4 的 Clone 工作应理解为扩展已有获取能力，不重复建设。

## 1. 文档目的

本文档用于描述 PyCode 从当前 `v1.0` 向 `v2.0` 演进过程中的主要开发目标、架构方向和实施顺序。

本文档只描述 **v2.0 阶段的工程化开发计划**。

更长期的能力，例如：

* Hybrid Retrieval
* Embedding / Vector Search
* Reranker
* 系统化 Evaluation
* 更复杂的 Python 静态分析
* 多语言代码分析
* MCP
* Coding Agent 深度集成
* Multi-Agent

不属于当前 v2 阶段的主要开发目标，后续单独规划。

# 2. 当前状态

PyCode v1.0 已经具备较完整的 Python Repository Intelligence 与 Agent 核心能力。

目前核心流程大致为：

```text
Python Repository
        ↓
     Scanner
        ↓
    AST Parser
        ↓
  Project Index
        ↓
   Code Graph
        ↓
    Retriever
        ↓
   LLM / Agent
```

现有能力主要包括：

* Python Repository 扫描
* AST 静态分析
* 类、函数、方法、Import 等代码信息提取
* Project Index
* Code Graph
* Retriever
* Repository QA
* Impact Analysis
* Agent Runtime
* Tool Calling
* Planner
* Todo
* Memory
* Trace
* Context 管理
* Task DAG
* Git Diff 相关分析
* pytest 测试
* Streamlit Demo

v1.0 已经证明了 PyCode 的核心 AI / Agent 思路。

当前主要不足已经从“Agent 能力不足”逐渐转变为：

* 缺乏标准 Web Backend
* 缺乏持久化业务模型
* 长任务主要以同步方式执行
* 缺乏完整的任务生命周期
* Agent Trace 尚未产品化
* 缺乏正式 Web 前端
* 部署和环境复现能力不足

因此 v2 的主要目标是进行工程化升级。

# 3. v2 总体目标

PyCode v2 的目标是：

> 将 PyCode 从一个本地运行的代码分析 Agent，升级为一个具备完整后端、持久化、异步任务、实时 Agent Trace、Web UI 和容器化部署能力的 AI 应用。

目标架构：

```text
                    Web Frontend
                         │
                    HTTP / SSE
                         │
                         ▼
                 ┌───────────────┐
                 │    FastAPI    │
                 │    Backend    │
                 └───────┬───────┘
                         │
              Application Services
                         │
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
       PyCode Core   PostgreSQL    Redis
             │                       │
             │                       ▼
             │                  Task Queue
             │                       │
             │                       ▼
             │                     Worker
             │                       │
             └───────────────────────┘
```

主要技术栈预计包括：

```text
Backend:
FastAPI

Persistent Storage:
PostgreSQL
SQLAlchemy
Alembic

Temporary State / Queue:
Redis

Background Execution:
Celery 或其他合适的 Worker 方案

Realtime:
SSE

Frontend:
React + TypeScript

Deployment:
Docker
Docker Compose
```

# 4. 核心架构原则

## 4.1 保持 PyCode Core 独立

现有：

```text
pycode/
```

继续作为独立的核心 Python Library。

其主要职责包括：

* Repository Scanner
* AST Parser
* Project Index
* Code Graph
* Retriever
* Impact Analysis
* Agent Runtime
* Agent Tools
* Context
* Memory
* Trace

不得为了接入 Backend，而直接让 `pycode/` 依赖：

* FastAPI
* SQLAlchemy
* Redis
* Celery
* React 等 Web / Infrastructure 技术

依赖方向应该始终保持：

```text
Frontend
    ↓
Backend
    ↓
Application Service
    ↓
PyCode Adapter
    ↓
PyCode Core
```

PyCode Core 不应该反向依赖 Backend。

# 5. Phase 1 — 稳定 PyCode Core

## 目标

在开始 Backend 开发之前，先确保当前 PyCode Core 有清晰稳定的调用边界。

## 主要工作

### 5.1 检查现有模块职责

重点确认：

```text
Scanner
Parser
GraphBuilder
Retriever
Query
Agent Runtime
Tools
Trace
Memory
Storage
```

之间的职责是否合理。

不要求进行大规模重构。

仅处理会明显阻碍 Backend 集成的问题。

---

### 5.2 统一 Core 调用入口

考虑建立一个上层入口，例如：

```text
PyCodeEngine
```

或：

```text
PyCodeAdapter
```

使 Backend 不需要直接了解大量内部模块。

期望调用形式类似：

```python
engine.index(...)
engine.ask(...)
engine.impact(...)
engine.run_agent(...)
```

---

### 5.3 保证现有测试稳定

重点保护：

* Parser
* Graph
* Retriever
* Query
* Agent
* Tools
* Storage

Backend 开发不应破坏现有 v1.0 核心行为。

## 完成标准

不依赖 CLI 或 Streamlit，也可以通过 Python API 稳定调用 PyCode 的核心能力。

# 6. Phase 2 — FastAPI Backend

## 目标

建立独立 Backend，使 PyCode 可以通过标准 HTTP API 使用。

主要 Repository Source 为公开 HTTPS Git URL。创建 Project 只登记 `name/repo_url/branch`，允许相同来源创建多个 Project；index 请求负责 UUID Workspace 准备、必要的 Clone、Index 和 Graph。Project 的业务元数据与服务器源码路径分离，前端不提交 `local_path`。

## 目录方向

建议新增：

```text
backend/
└── app/
    ├── main.py
    ├── api/
    ├── schemas/
    ├── services/
    ├── infrastructure/
    ├── integrations/
    └── core/
```

---

## Backend 调用关系

严格保持：

```text
FastAPI Router
      ↓
Application Service
      ↓
PyCode Adapter
      ↓
PyCode Core
```

Router 只负责：

* HTTP 参数处理
* 请求验证
* Response
* HTTP Status Code
* Dependency 获取

不要在 Router 中直接实现大量 PyCode 业务逻辑。

---

## 第一批 API

至少包括：

```text
GET  /health

POST /api/v1/projects
GET  /api/v1/projects/{project_id}

POST /api/v1/projects/{project_id}/index

POST /api/v1/projects/{project_id}/ask

POST /api/v1/projects/{project_id}/impact
```

初期可以保持同步调用。

Phase 2 保持单进程、内存 Project Store，状态 created → preparing → indexing → ready，失败为 failed。创建不产生 Workspace；index 首次浅 Clone，后续复用当前工作区，不自动 pull。重启不删除源码和产物，但需重新登记为新 Project 并重新获取；不自动认领旧目录。

仓库获取由 Service 调用 Backend infrastructure，准备好本地目录后再交给 PyCodeAdapter。仅允许配置公共 Host 的无凭证 HTTPS URL，禁用交互认证与重定向，Git 操作超时；隔离 Git 配置并在 checkout 前拒绝符号链接、子模块和仓库自带 `.pclens`。分析前再次验证目录边界，不安装依赖、不运行仓库程序或测试。复杂网络出口和执行 Sandbox 留待后续设计。

此阶段重点是先验证：

```text
HTTP
↓
FastAPI
↓
Service
↓
PyCode
↓
Response
```

整个链路是否成立。

## 完成标准

不使用 CLI 和 Streamlit，也能够通过 HTTP API 使用 PyCode 的主要能力。

离线测试覆盖登记 → Clone → Index / Graph → Ask / Impact；保留 Phase 1 全部回归。数据库、Snapshot、Worker、SSE 不属于本阶段范围。

# 7. Phase 3 — PostgreSQL 持久化

## 目标

让 PyCode 从本地工具转变为具有持久业务状态的 Backend Application。

第一阶段重点建立四类核心数据模型。

---

## 7.1 Project

表示 PyCode 管理的一个代码仓库。

建议包含：

```text
id
name
repo_url
branch
status
created_at
updated_at
```

---

## 7.2 ProjectSnapshot

表示某个 Repository 在特定 Git Commit 下的分析状态。

建议包含：

```text
id
project_id
commit_sha

index_artifact_path
graph_artifact_path

file_count
node_count
edge_count

status
created_at
```

结构：

```text
Project
   │
   ├── Snapshot @ commit A
   ├── Snapshot @ commit B
   └── Snapshot @ commit C
```

---

## 7.3 AgentRun

表示一次 Agent 执行。

建议记录：

```text
id
project_id
snapshot_id

task
run_type

status

model

prompt_tokens
completion_tokens

result
error_message

started_at
finished_at
```

---

## 7.4 TraceEvent

记录结构化 Agent 执行事件。

建议包含：

```text
id
run_id
sequence

event_type
tool_name

payload

created_at
```

---

## 数据存储原则

PostgreSQL 保存：

```text
Project
Snapshot Metadata
AgentRun
TraceEvent
业务状态
```

现有：

```text
index.json
code_graph.json
repository snapshot
```

第一版继续作为 Artifact 保存。

不要为了使用 PostgreSQL，就把所有 Code Graph Node / Edge 全部关系化。

---

## 使用技术

```text
PostgreSQL
SQLAlchemy
Alembic
```

数据库 Schema 修改必须通过 Migration。

## 完成标准

应用重启以后：

* Project 不丢失
* Snapshot 不丢失
* Agent Run 不丢失
* Trace 历史可以查询

# 8. Phase 4 — Repository 与 Snapshot 生命周期

## 目标

让 Git Repository 成为 PyCode 中真正受管理的资源。

在 Phase 2 已有的基本 Clone / Workspace 能力上扩展更新与版本生命周期；创建与获取仍为两个独立操作。下面的完整流程描述多个操作的组合，不要求创建接口同步执行全部步骤。

完整流程：

```text
Create Project
      ↓
Clone Repository
      ↓
Resolve Branch
      ↓
Resolve Commit SHA
      ↓
Create Snapshot
      ↓
Build Index
      ↓
Build Code Graph
      ↓
Save Artifacts
      ↓
Snapshot Ready
```

需要处理：

* Repository Clone 失败
* Branch 不存在
* Repository 更新
* Index 失败
* Code Graph 生成失败
* 相同 Commit 已经分析
* Repository Snapshot 历史

核心原则：

> 每一次代码分析都应该对应一个明确的 Git Commit。

这样未来才能可靠支持：

```text
Commit A
vs
Commit B
```

以及：

```text
Git Diff
Impact Analysis
```

## 完成标准

任何 PyCode 分析结果，都能够追溯到具体：

```text
Project
+
Commit SHA
+
Snapshot
```

# 9. Phase 5 — Redis 与后台 Worker

## 目标

将耗时任务从 FastAPI HTTP 请求生命周期中移出。

以下操作可能成为后台任务：

```text
git clone

repository indexing

Code Graph generation

Agent Run
```

---

## 初步架构

```text
Client
   ↓
FastAPI
   ↓
Create Task / AgentRun
   ↓
Redis
   ↓
Worker
   ↓
PyCode Core
```

API 不再等待整个任务完成。

例如：

```text
POST /agent-runs
```

立即返回：

```json
{
  "run_id": "...",
  "status": "queued"
}
```

---

## Task 状态

统一采用：

```text
queued
↓
running
↓
completed
```

失败则：

```text
queued
↓
running
↓
failed
```

---

## Redis 第一阶段用途

Redis 可用于：

* Task Queue
* 实时任务进度
* 短期缓存
* 防重复任务 Lock
* Agent Event
* 临时状态

Redis 不作为永久业务数据的唯一来源。

---

## 需要处理的工程问题

逐渐支持：

```text
Retry
Timeout
Idempotency
Duplicate Task Prevention
Worker Failure
```

## 完成标准

耗时 Agent 或 Indexing Task 不再长时间阻塞 FastAPI 请求。

---

# 10. Phase 6 — Agent Trace 结构化

## 目标

把现有 Trace 从调试能力升级成正式的应用能力。

统一 Agent Event。

例如：

```text
run_started

plan_created

tool_started

tool_finished

context_updated

llm_started

llm_finished

run_completed

run_failed
```

Event 应该是结构化数据，而不是单纯输出字符串。

例如：

```python
TraceEvent(
    event_type="tool_started",
    tool_name="query_graph",
    payload={...},
)
```

最终应该能够根据 Trace：

> 还原一次 Agent Run 到底做了什么。

## 完成标准

每一个 Agent Run 都具有结构化、可查询的完整执行 Trace。

---

# 11. Phase 7 — SSE 实时 Agent Trace

## 目标

让前端可以实时观察 Agent 的执行过程。

目标数据流：

```text
Worker
   ↓
Redis Stream
   ↓
FastAPI
   ↓
SSE
   ↓
Frontend
```

例如客户端实时看到：

```text
开始分析 Repository

↓

定位目标 Symbol

↓

查询 Caller

↓

读取相关文件

↓

查询相关测试

↓

生成分析结果
```

建议提供：

```text
GET /api/v1/agent-runs/{run_id}/events
```

需要考虑：

* 客户端断开
* SSE 重连
* Run 已结束
* 历史 Trace 查询

## 完成标准

Agent 执行期间，浏览器可以实时看到 Trace Event。
