### P1-01：Windows 沙箱临时目录初始化失败（已处理）

修改前直接运行完整测试，使用 `tmp_path` 的测试出现 setup error；单独使用新目录运行 Scanner 测试仍出现同类错误，错误报告未能正常结束，两次执行手动中止。未取得完整错误堆栈或有效汇总，不能据此认定业务失败。

经授权在沙箱外、使用新的临时目录重跑，205 项现有测试全部通过（17.91 秒）。这是 CLI 迁移前的兼容基线；此时新增 Engine 和包导出已存在，但 CLI 尚未接入。后续测试同样在沙箱外运行，不引入 pytest 包装器或修改项目权限逻辑。

手动示例在沙箱内也出现明确 `PermissionError: [WinError 5]`，无法访问 `TemporaryDirectory` 刚创建的副本目录，清理同样被拒绝；授权在沙箱外执行相同示例后通过。首次失败留下的目录位于忽略的 `.pytest_tmp_v2_phase1_manual_demo`，未清理其他已有测试目录。

### P1-02：CLI 混合编排和展示（已迁移并通过回归）

原索引、图谱、问答和 Agent 命令同时承担调用与打印。新增 Engine 集中编排，CLI 只渲染返回结果；问答通过 `AnswerResult` 保留检索对象和证据，CLI 仍返回字符串。Artifact 错误提示保持兼容。

### P1-03：两种路径语义必须分别保留（已通过回归）

显式索引／图谱输出和普通 query 的 graph 路径沿用当前工作目录语义；Agent graph 路径按“绝对路径 → 当前工作目录下已有文件 → 项目内已有文件 → 原路径”解析。解析移至 Engine，不统一改为项目相对路径；工具仍执行项目内路径权限检查。

### P1-04：planner 副作用与内部状态写入（本阶段保留）

`plan_task()` 会更新传入 `AgentTask.task_type`。Engine 复用 `run_agent_task()` 每次创建任务，避免共享调用状态，不变更 planner 契约。Memory／Task DAG 可能写入 `.pclens`；关闭自动 Memory 提取不等于禁止全部内部状态工具。默认不运行测试、不改源代码、不提交 Git 的边界保持不变。

### P1-05：新测试对现有 Agent 行为的两个假设不准确（已修正并通过复测）

首次定向测试 43 passed / 2 failed：第二个隔离项目只有顶层 print，没有静态入口线索，因此不能要求入口检索返回非空证据；未授权的 `run_tests` 在 LLM action 校验阶段就被拒绝，不一定进入 Executor 并生成 ToolResult。

修正测试项目以包含独立入口；分别验证 `run_tests` 的规划阶段拒绝和一般非只读工具的 Executor policy 拒绝。保留对不执行工具、fallback Trace、授权参数传递的断言，不修改 Runtime／Policy 语义。

第二次定向测试 46 passed / 1 failed：在 `other.py` 中增加 main guard 仍不足以匹配现有 Query 的入口启发式，该查询按入口文件名或名为 main 的函数识别。最终将隔离项目入口命名为 `app.py`，保持不同项目使用不同文件名以检查证据不混用。此限制属于既有静态查询能力，不在 Phase 1 扩展。

# Phase 2 — FastAPI Backend

日期：2026-09-09。状态：已完成（Git Repository Source 补充、Backend 定向回归和完整回归通过；3 项真实符号链接用例受 Windows 权限限制跳过）。

## 1. 计划开发内容

- 建立 Router → Application Service → PyCodeAdapter → PyCodeEngine 分层，同步执行六个接口：health、创建／查询项目、index、ask、impact。
- 对外 Project 契约使用 `name`、`repo_url`、可选 `branch` 和状态；创建只登记，不 Clone，允许相同 Repository 创建多个 Project，服务器绝对路径不进入响应。
- index 在 `<workspace_root>/<project_id>/repo` 准备源码：缺少仓库时 Clone，存在时复用且不自动 pull；然后通过现有 Adapter 调用 Core 生成 Index 和 Code Graph。
- 使用应用内存 Store，单进程同步请求；状态支持 created → preparing → indexing → ready，任一步失败进入 failed，并保留安全错误信息和重试能力。
- Git ingestion 只允许配置 Host 上无内嵌认证的 HTTPS URL，关闭交互、隔离 Git 配置、限制协议和重定向并设置 timeout；不递归 submodule，不运行仓库代码、安装、脚本或测试。
- Clone checkout 前拒绝 Git tree 中的符号链接、submodule 和 `.pclens`，落盘后验证 Workspace 文件边界；新增离线真实 Git 与假 LLM HTTP 测试。
- 保持 Router → Service → Adapter → Core 分层，不修改无关 Core；不实现 PostgreSQL、ProjectSnapshot、Redis、Worker、自动远程更新、SSE 或前端。

## 2. 问题与解决方法

- **依赖安装权限（已处理）**：沙箱阻止 pip 写入临时构建目录；授权在沙箱外重试后安装成功，未修改项目权限或引入包装器。
- **环境依赖与声明不一致（已校正并通过完整回归）**：原环境 OpenAI SDK 为 2.41.1，与项目既有 `<2.0` 声明不符；安装时解析为 1.109.1。保留原依赖约束。实际版本：FastAPI 0.141.1、Starlette 1.3.1、Pydantic 2.13.4、Uvicorn 0.50.2、HTTPX 0.28.1；`pip check` 已通过。
- **导入隔离测试误把测试工具算作应用依赖（已修正并通过复测）**：HTTPX 的可选 CLI 导入 Rich，导致禁止展示依赖的子进程测试失败；改为隔离验证应用创建和 OpenAPI，HTTP 行为仍由真实 TestClient 测试覆盖，不改变后端架构。
- **Windows 符号链接权限限制**：3 项真实符号链接测试因 OS 不允许创建链接而跳过；另加不依赖系统特权的路径解析越界测试，验证 impact 和 Artifact IO 在解析出项目外路径时拒绝执行。
- **测试客户端弃用提示**：Starlette 1.3.1 提示未来迁移到 HTTPX2；当前 HTTPX 测试可运行。本阶段按计划保留 HTTPX，不隐藏警告或增加未经需要的依赖迁移。
- **Git checkout 的隐藏执行面（已处理）**：仅使用 `shell=False` 仍可能继承用户 Git 配置、credential helper、hooks、fsmonitor 或 smudge filter。实现改为隔离系统／全局配置和环境变量，关闭交互与 hooks，禁止重定向和非 HTTPS protocol，跳过 LFS smudge，并在 checkout 前检查 tree。离线测试注入恶意 filter 配置和仓库脚本，确认均未执行。
- **Windows 可能把 Git symlink 落为普通文件（已处理）**：不能只依赖文件系统 `is_symlink()`。Clone 先 `--no-checkout`，通过 `git ls-tree` 的 mode 拒绝符号链接和 submodule，再 checkout；该测试不需要 Windows 创建链接权限并已通过。
- **修改前测试的沙箱临时目录权限（已处理）**：首次在沙箱中执行出现大量 setup error，未计为业务测试结果；使用新的 pytest 临时目录在沙箱外重跑，获得 292 passed / 0 failed / 3 skipped 的有效基线。没有修改业务语义掩盖环境问题。

### P4-05：Snapshot、Artifact 与分析版本语义（已完成）

- Snapshot 状态机为 `indexing → ready | failed`；Commit resolve 后、长耗时分析前创建或复用 `(project_id, commit_sha)` 唯一行。同 Commit 失败重试和 Artifact repair 更新原行，不生成重复 Snapshot。
- `projects.current_snapshot_id` 只允许由 Repository 指向同 Project 的 ready Snapshot。Project 操作状态与当前可用分析版本分离：新 B 失败时 Project 为 failed 并记录安全错误，但旧 ready A 继续作为 current，GET 仍返回 A 的 `index_summary`。
- ask／impact 不再以 `Project.status == ready` 为唯一条件，而是验证 current Snapshot 属于 Project、状态 ready、Commit object 可用且独立 Artifact bundle 完整有效；每个 AgentRun 明确绑定实际使用的 Snapshot。因此 B 失败而 A 仍 current 时，ask／impact 会 checkout exact A 并继续服务。
- Artifact 保存于受控 Project 目录下的 `artifacts/<snapshot_id>/`，包含 `index.json`、`code_graph.json` 和带 Project／Snapshot／Commit／统计值／SHA-256 的 manifest；数据库只保存相对路径和统计元数据。A/B bundle 相互独立，不会被下一次分析覆盖。
- 发布先在同一 Artifact root 的唯一 staging 目录完整构建和验证，再将旧 final 重命名为唯一 backup、将 staging 重命名为 final；第二次 rename 失败会恢复 backup。该实现不使用 `os.replace` 覆盖 Windows 非空目录，残留 backup 可在后续操作恢复或安全清理。
- 如果 Artifact 已发布而数据库激活失败，Snapshot 留为 failed；下次相同 Commit 索引会校验已发布 bundle 并完成数据库激活，不重复运行 Core。
- Phase 3 当前 Snapshot 的 `repo/.pclens` 在首次 index／ask 使用时校验 HEAD、内容和统计值后 lazy archive，并建立 Commit 保护 ref。非 current 的 Phase 3 历史行不会在首次 Phase 4 操作中被无谓改写；其 Commit 再次成为目标时按现有唯一 Snapshot 行执行可恢复 repair。
- 数据库事务保持短小，不跨越 Clone／Fetch／Checkout／Index／Graph／Artifact IO；同一 Project 的完整流程仍由 `ProjectOperationLocks` 单进程锁保护，不同 Project 可并行。

### P4-06：失败语义与恢复结果

| 失败点 | 新目标 Snapshot | Project | 原 current ready Snapshot |
|---|---|---|---|
| Clone／Fetch／branch resolve | 尚未创建 | failed + 安全 last_error | 保留且仍可用于 ask／impact |
| Checkout／Commit／HEAD 校验 | failed | failed + 安全 last_error | 若目标为新 Commit则保留；目标即 current repair 时清除无效 current |
| Index／Graph／Artifact publish | failed，不保存半完成统计 | failed + 安全 last_error | 新 Commit失败不影响旧 current |
| Artifact 已发布、DB 激活失败 | 数据库保持 failed，可重试 | failed | 新 Commit场景仍保留旧 current；重试复用完整 bundle |
| current Artifact 缺失／损坏或 Commit 不可用 | current Snapshot 标 failed | failed，current 清空 | 不再作为有效分析版本；重新 index 可 repair |

所有返回客户端的错误继续隐藏 SQL、连接串、凭据、Git stderr、源文件内容和内部 Stack Trace；内部日志保留异常链供诊断。

### P4-08：人工验收 Git 网络环境与失败可观测性修复（已完成）

首次 Repository Index／Refresh 人工验收出现间歇性 `repository_failed`。外部手工 Git 已确认 Repository、branch、Commit、full clone、remote tracking ref、tree 和 detached checkout 均正常；失败请求结束后没有保留 Git stage／stderr，因此不能把某一个历史 Git 命令或 Proxy／CA 缺失表述为已经 100% 证明的唯一根因。

代码审查确认了两项实现问题：

1. `_run()` 只继承最小 OS 环境，丢弃了 Backend 运行环境中的 Proxy／CA 设置；这是手工 Git 成功而隔离 Git 失败的最高概率原因。
2. subprocess 已捕获 returncode／stdout／stderr，但旧实现只映射通用 BackendError，没有安全记录失败 stage 和 stderr，导致 Uvicorn 现场只有 access log，无法追溯历史失败。

最小修复内容：

- 在继续隔离 HOME、Git system/global config、credential helper、hook、attribute、protocol 和 submodule 行为的前提下，只额外允许传递 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` 及其小写形式，以及 `SSL_CERT_FILE`、`SSL_CERT_DIR`、`GIT_SSL_CAINFO`。
- 不允许继承 `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_*`、`GIT_CONFIG_VALUE_*`、`GIT_PROXY_COMMAND`、`GIT_SSL_NO_VERIFY`；其他环境变量仍不在白名单中。
- 未允许 `CURL_CA_BUNDLE`：它是 curl 命令环境入口，不是当前 Git/libcurl 集成的文档化 Git TLS 控制；现有 `GIT_SSL_CAINFO` 和 OpenSSL `SSL_CERT_FILE／DIR` 已覆盖所需最小能力。
- Proxy／CA 值只传入 Git subprocess，不进入日志、Project.last_error 或 API Response。
- 为 Git 调用加入 `resolve_remote_branch`、`detect_shallow`、`clone_repository`、`unshallow_repository`、`fetch_remote_branch`、`resolve_remote_commit`、`validate_commit_tree`、`protect_snapshot_ref`、`checkout_commit`、`clean_workspace`、`verify_head` 等明确 stage。
- Git 失败通过 Uvicorn error logger 记录 project_id、stage、operation、经过校验的 remote host／branch、returncode、timeout 和最长 2048 字符的脱敏 stderr；不记录 subprocess environment 或完整 URL。URL、Authorization、Proxy-Authorization、Bearer、token/password 参数和常见 GitHub token 格式均会脱敏。
- API 和 Project.last_error 继续使用原有通用安全错误，不向客户端公开 Git stderr。
- 没有增加任何自动 retry，避免掩盖真实失败。

新增回归验证：

- 环境白名单测试确认 HTTPS_PROXY、NO_PROXY、SSL_CERT_FILE、GIT_SSL_CAINFO 进入 Git subprocess；危险 Git 配置变量和 CURL_CA_BUNDLE 不进入。
- 日志测试使用包含 proxy user/password、token、Authorization 和超长内容的模拟 stderr，确认 stage／returncode 可见，而所有敏感值均不出现并正确截断。

# Phase 5D-1A — Execution Correctness Foundation

日期：2026-09-14。状态：Phase 5D Reliability Audit 已通过；5D-1A 代码实现、自动化验收、真实 PostgreSQL 并发 Claim 验证和真实 Redis 锁集成验证均已完成，双 Worker 人工 E2E 待执行。本阶段只处理 BackgroundTask 原子 Claim、重复 Celery delivery 安全 no-op，以及 Project 级 Redis 分布式锁；不实现 API Idempotency-Key、retry、timeout、late ACK、worker lease、stale running recovery、Transactional Outbox 或 5D-1B 后续内容。

## 1. BackgroundTask 原子 Claim（已完成）

- 新增 `BackgroundTaskClaimStatus` 和 `BackgroundTaskClaim`，Claim 结果明确限定为 `CLAIMED`、`ALREADY_RUNNING`、`TERMINAL`、`NOT_FOUND`。
- BackgroundTask Repository protocol、新旧内存实现和 SQLAlchemy 实现统一提供 `claim(task_id)`。PostgreSQL 使用单条条件 `UPDATE ... WHERE id=:id AND status='queued' RETURNING` 抢占执行权，并在同一语句中切换到 running、增加 `attempt_count`、写入 `started_at` 和清理旧错误字段。
- 条件更新没有命中时，Repository 读取当前持久化状态并区分 running、终态和不存在；不会因为重复 delivery 再次增加 `attempt_count`。
- 内存 Repository 在 UnitOfWork 的可重入事务锁内执行等价状态转换，为普通单元测试提供与 PostgreSQL 一致的并发语义。
- 保留 `mark_running()` 作为兼容入口，但其内部复用 Claim，并继续为直接生命周期调用者保持原有冲突错误行为。

## 2. 重复 Delivery 与 AgentRun 一致性（已完成）

- `BackgroundTaskService` 只有在 Claim 返回 `CLAIMED` 时才调用实际业务逻辑；`ALREADY_RUNNING` 和 `TERMINAL` 直接记录日志并安全返回，不执行第二次业务调用、不写 failed，也不覆盖已有终态。
- Agent 任务以 BackgroundTask Claim 作为唯一执行入口。只有 Claim 获胜者可以在同一数据库事务中把关联 AgentRun 从 queued 改为 running；原先对 BackgroundTask 的第二次 running 更新已移除。
- 对运行中或终态 Agent 重复 delivery，服务验证 BackgroundTask 与 AgentRun 的关联字段、snapshot 和状态对是否一致；一致时 no-op，不再次调用 Agent Core。
- BackgroundTask／AgentRun 缺失关联、关联到错误 run、snapshot 不一致或状态组合不一致时，抛出稳定的 `background_task_consistency_error`。如果当前执行刚赢得 Claim，整个事务会回滚，不留下 BackgroundTask running、AgentRun queued 的半状态。
- `project_lock_unavailable`、`project_lock_lost` 映射为 HTTP 503，`background_task_consistency_error` 映射为 HTTP 500；公开 API 请求和响应字段没有变化。

## 3. Project 级 Redis 分布式锁（已完成）

- 生产锁键统一为 `pycode:lock:project:{project_id}`。FastAPI 和 Celery Worker 通过相同 composition factory 创建 Redis lock backend，不再依赖各进程互不共享的 `threading.Lock`。
- 获取锁使用 Redis `SET key token NX PX ttl`；每次持有生成独立随机 token。同一 Project 已被占用时立即返回现有 `project_busy`，本阶段不等待、不排队、不自动重试；不同 Project 使用不同键，可以并行执行。
- 解锁使用 Lua 原子比较 token 后删除，续租使用 Lua 原子比较 token 后执行 `PEXPIRE`。过期旧持有者不能删除或续租后来持有者的锁。
- 增加 daemon renewal thread 和显式所有权检查。默认 TTL 为 300 秒、续租周期为 60 秒，可由 `PYCODE_PROJECT_LOCK_TTL_SECONDS` 和 `PYCODE_PROJECT_LOCK_RENEW_SECONDS` 配置。
- Redis URL 缺失、Redis 不可用或脚本执行失败统一转为安全的 `project_lock_unavailable`；续租失败、token 被替换或无法确认所有权时标记 lock lost，并在业务边界抛出 `project_lock_lost`。
- 测试注入的 `InMemoryPersistence` 继续使用语义等价的内存 lock backend，支持 token、过期、续租和非 owner 释放检查，不要求普通 unit/API 测试连接 Redis。

## 4. Project 操作接入与锁丢失语义（已完成）

- Repository Indexing、exact Snapshot Agent execution、同步 ask 和同步 impact 全部使用同一 Project 锁命名空间，因此 API 与 Worker、索引与 Agent 之间不会形成两套互斥域。
- Indexing 在仓库同步后、发布前后和激活前检查锁所有权；Agent 在进入 Core 前、Core 返回后和终态提交前检查所有权；同步 ask／impact 在业务调用返回后和 BackgroundTask completed 前再次检查。
- 检测到 lock lost 后，旧执行者不会继续报告 completed。Indexing 的旧持有者还会跳过可能覆盖新持有者状态的 Project／Snapshot 失败清理；外层 BackgroundTask 仍记录自身的安全失败状态。
- FastAPI 与 Worker 的 Redis client 采用 lazy 创建，模块导入和应用构造阶段不会主动连接 Redis。

# Phase 5D-1B — Submission Idempotency & Active Index Prevention

日期：2026-09-14。状态：代码实现、migration 往返、目标测试、真实 PostgreSQL 并发测试、Phase 5D-1A 回归、Backend 回归和全仓库回归均已完成；HTTP 手工 E2E 步骤已给出但本轮未另行启动服务执行。本阶段只增加 HTTP submission idempotency 和 Repository Index active duplicate prevention，不改变 Worker retry／ACK／timeout／recovery 语义。

## 1. Idempotency-Key HTTP 契约（已完成）

- `POST /api/v1/projects/{project_id}/index` 与 `POST /api/v1/agent-runs` 接受可选 `Idempotency-Key` Header；不提供 Header 时现有客户端继续兼容。
- Header 作为大小写敏感的 opaque token 使用，不自动 lower-case、不解析业务含义。显式提供时必须包含 1～255 个字符，不能全为空白，也不能包含 ASCII 控制字符；非法值返回 HTTP 422。
- 相同 scope、相同 key、相同 request fingerprint 返回原有持久化资源并保持 HTTP 202。Index 返回原 `task_id`；Agent 返回原 `run_id` 与 `task_id`；response status 读取当前数据库状态，不伪造 queued。
- 相同 scope 和 key 绑定到不同 fingerprint 时返回 HTTP 409、稳定错误码 `idempotency_conflict`，不会创建或 enqueue 第二个资源。

## 2. Scope、Fingerprint 与持久化（已完成）

- Idempotency scope 为 `(task_type, project_id, idempotency_key)`；相同 key 可在不同 Project 复用，也可分别用于 `repository_index` 和 `agent_run`。
- fingerprint 使用经过 API validation 的业务值构造 canonical JSON：`sort_keys=True`、固定 `(',', ':')` separators、`ensure_ascii=False`、UTF-8 编码，最后计算 SHA-256 hex；未使用跨进程不稳定的 Python `hash()`。
- Repository Index fingerprint 只包含 `operation=repository_index` 和 path 中的 `project_id`；不包含 current snapshot、remote HEAD、Commit SHA 或 Project.status。
- AgentRun fingerprint 只包含 `operation=agent_run`、`project_id` 和验证后的 `task`；不包含 Idempotency-Key 或 current snapshot。replay 因此继续返回第一次固定 Snapshot 的原 AgentRun。
- `background_tasks` 新增 nullable `idempotency_key VARCHAR(255)` 和 `request_fingerprint VARCHAR(64)`；二者通过 check constraint 保证同时为 NULL 或同时非 NULL。绑定生命周期随 BackgroundTask 记录保留，不引入 Redis TTL 或独立 idempotency table。

## 3. 数据库 Race Protection（已完成）

- Alembic revision `20260914_0004` 在 PostgreSQL 创建 partial unique index `uq_background_tasks_idempotency_scope`：`(task_type, project_id, idempotency_key) WHERE idempotency_key IS NOT NULL`。
- 同一 Project 最多一个 queued／running Repository Index，由 partial unique index `uq_background_tasks_active_repository_index` 保证：`UNIQUE(project_id) WHERE task_type='repository_index' AND status IN ('queued','running')`。
- SQLAlchemy Repository 使用 PostgreSQL `INSERT ... ON CONFLICT DO NOTHING RETURNING` 原子尝试创建。未返回新行时先读取相同 idempotency scope 并比较 fingerprint，再读取 active index；数据库约束而非 process-local lock 是最终并发保护。
- same-key 并发 loser 会等待 winner 的唯一索引冲突决议，然后读取 winner 并返回同一资源；不同 key 的 concurrent Index loser 转换为 `repository_index_in_progress`，不会暴露 UniqueViolation、IntegrityError 或 HTTP 500。
- Memory Repository 在现有 UnitOfWork 可重入事务锁内实现相同 lookup、fingerprint conflict、active index prevention 和 create-or-get 语义；真实并发正确性由 PostgreSQL 测试验证。

## 4. Repository Index Submission（已完成）

- 判断顺序固定为：先按 scope 解析 idempotent replay／conflict；只有没有既有 binding 时才尝试创建 active Index。
- active Index 已存在时，新 key、不同 key 或无 key 请求均返回 HTTP 409、`repository_index_in_progress`，message 固定为 `An index operation is already queued or running for this project.`。
- 已有 task 进入 completed／failed 后，active partial index 自动释放，新 key 或无 key 时可创建新 Index；旧 key 与相同 fingerprint 仍永久 replay 原 task。
- 只有 Repository 返回 `created=True` 的新 BackgroundTask 才调用 `enqueue_repository_index`；replay 和 active conflict 均不 enqueue。

## 5. AgentRun Submission（已完成）

- 新 Agent submission 在同一事务中先原子插入尚未关联 run 的 BackgroundTask；winner 随后验证 current ready Snapshot、创建 queued AgentRun，并把 `agent_run_id` 和固定 `snapshot_id` 回填到 BackgroundTask 后整体 commit。
- 任一步骤失败会回滚整个事务。concurrent loser 不创建 AgentRun，只在 winner commit 后读取已经完整关联的 BackgroundTask／AgentRun，因此数据库最终保持 `1 AgentRun + 1 BackgroundTask`，不会出现孤立或数量不一致。
- replay 会验证持久化关联与 project／snapshot 一致性，并返回原资源；即使 Project.current_snapshot 从 A 变为 B，仍返回固定到 A 的原 AgentRun。
- 不提供 key 时，相同 task 文本的每次合法 POST 都创建新 AgentRun；使用不同 key 时同样允许创建，不做 `project_id + task text` 自动去重。
- 只有新建 Agent BackgroundTask 才调用 `enqueue_agent_run`；replay、fingerprint conflict 均不会再次 enqueue 或调用 Agent Core。

# Phase 5D-4B — Queued Orphan Reconciliation

日期：2026-09-14。状态：实现、migration 往返、真实 PostgreSQL 并发测试、跨阶段回归和全仓库回归均已完成。本阶段只恢复尚未确认 broker publish 的 `queued` BackgroundTask，不处理 running stale、Worker crash 后恢复、业务 retry、Celery ACK/redelivery 或 Transactional Outbox。

## 1. queued orphan 与持久化模型（已完成）

- 本阶段候选严格定义为 `status='queued' AND enqueue_confirmed_at IS NULL AND next_enqueue_attempt_at <= now()`；`running`、`completed`、`failed` 和已经确认 publish 的 queued task 均不参与扫描。
- `background_tasks` 新增 `enqueue_attempt_count`、`last_enqueue_attempt_at`、`enqueue_confirmed_at`、`next_enqueue_attempt_at`。`enqueue_attempt_count` 只计算 broker publish reservation/attempt；既有 `attempt_count` 仍只在 Worker 原子执行 `queued -> running` claim 时增加。
- 新任务在第一次数据库 commit 前即写入 `enqueue_confirmed_at=NULL` 和 `next_enqueue_attempt_at=created/submit time + publish grace`。因此 API 进程即使在 commit 后、调用 `send_task()` 前崩溃，任务仍可被后续 scanner 发现。
- 初始 `send_task()` 前先持久化本次 enqueue reservation；成功返回后写入 `enqueue_confirmed_at` 并清空 `next_enqueue_attempt_at`。失败仍按既有契约返回 HTTP 503 `task_queue_unavailable`，BackgroundTask 保持 queued、未确认并保留下一次尝试时间，不会被标记 failed。
- API 的 BackgroundTask 查询响应暴露上述四个 metadata 字段，以便诊断 initial publish 与 reconciliation 状态；未增加公开 reconcile HTTP API。

必须区分三种计数：HTTP submission 次数不等于 broker enqueue attempt 次数，也不等于 business `attempt_count`。例如客户端用同一 Idempotency-Key 请求两次只创建一个 BackgroundTask；initial publish 失败、reconcile publish 成功会得到 `enqueue_attempt_count=2`；Worker 真正 claim 一次后才得到 `attempt_count=1`。

## 2. Migration 与候选索引（已完成）

- Alembic revision `20260914_0005` 以 `20260914_0004` 为直接父 revision，当前保持单 head。
- migration 添加四个 enqueue metadata 字段和 `enqueue_attempt_count >= 0` check constraint；已有 queued task 回填 `next_enqueue_attempt_at=now()`，使升级前遗留的未决 queued row 可进入安全重发流程。
- scanner 使用 partial index `ix_background_tasks_queued_unconfirmed_next`：索引列为 `next_enqueue_attempt_at`，谓词为 `status='queued' AND enqueue_confirmed_at IS NULL`，与实际候选查询一致，没有增加无关索引。
- migration 测试实际执行 `0004 -> 0005 -> 0004 -> head`，核对字段、check constraint、partial index 和 downgrade 清理，最终 Alembic head 为 `20260914_0005`。

## 3. QueuedTaskReconciler 与并发 reservation（已完成）

- 新增 backend-owned `QueuedTaskReconciler`，职责仅为批量查询候选、在数据库事务中 reserve、按已有 dispatcher 重发相同 `BackgroundTask.id`、成功后确认 publish、失败后等待 backoff。它不调用 ProjectService、Agent Core、Git checkout 或 Tool，也不修改 AgentRun、Snapshot 和 BackgroundTask business status。
- SQLAlchemy Repository 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 获取有限批次。reservation 在 publish 前 commit，同时增加 `enqueue_attempt_count`、记录 `last_enqueue_attempt_at`，并把 `next_enqueue_attempt_at` 推到未来；并发 scanner 因行锁/跳锁和新的 future deadline 不会在同一 window 重复 reserve。
- Memory Repository 在共享 UnitOfWork 锁下实现等价业务语义；真实并发正确性由 PostgreSQL 双 Session 测试证明。
- backoff 独立基于 `enqueue_attempt_count`，集中采用 `5s, 15s, 30s, 60s` 后指数增长并受 `PYCODE_QUEUED_RECONCILE_MAX_BACKOFF_SECONDS` 上限约束。无最大尝试次数或永久失败策略；Redis 持续不可用时任务始终 queued。
- task type 通过现有统一 dispatcher 映射，支持 `repository_index`、`agent_run` 和自然共用 BackgroundTask 的 `health`；未知类型仅记录错误并推迟下次尝试，不执行任意 Celery task name。
- 日志包含 reconciliation start/completion、candidate count、reservation/skip、task id/type、enqueue attempt count、next attempt time、publish success/failure；不记录 Agent task/prompt 正文。

## 4. Repository Index、AgentRun 与 Idempotency 边界（已完成）

# Phase 5D-2 — Error Taxonomy, Bounded Timeout & Safe Retry

日期：2026-09-14。状态：实现、migration 往返、真实 PostgreSQL 并发测试、跨阶段回归及全仓库回归均已完成，等待代码审查。本阶段只建立错误性质、关键外部 I/O bounded timeout、Agent Core 持久化 no-retry boundary，以及 Repository Git 网络子操作的局部有限 retry；没有实现 Agent/Repository/Celery whole-task retry、Worker crash recovery、late ACK、lease、heartbeat、stale-running recovery、Outbox 或 hard task kill。

## 1. Backend Error Taxonomy

- `BackendError` 继续作为主要异常载体；Backend Core 新增 `ErrorKind`：`PERMANENT`、`TRANSIENT`、`CONSISTENCY`、`TIMEOUT`，以及集中式 `ErrorSpec(code, kind, http_status)`/`ERROR_CATALOG`。
- FastAPI error handler 改为读取中央 catalog；原 `ERROR_STATUS` 保留为兼容导出，既有公开 `error_code` 与 HTTP status 未改变。本阶段未新增公开错误码。
- `repository_timeout`、`model_timeout` 分类为 `TIMEOUT`；`project_busy`、`project_lock_unavailable` 分类为 `TRANSIENT`，但仍 fail-fast；`project_lock_lost`、`repository_changed`、数据库冲突/失败及后台任务一致性错误分类为 `CONSISTENCY`。
- 无法可靠证明 transient 的 `repository_failed`、`model_failed` 以及未知 code 安全归为 `PERMANENT`；未知 code 的 HTTP fallback 仍为 500。
- `ErrorSpec` 没有 `retryable` 布尔值。是否 retry 必须由 operation、execution phase、具体 code 与 attempt context 决定；`TIMEOUT` 或 `TRANSIENT` 本身不授权业务重试。

## 2. Bounded 外部 I/O

- Redis project-lock client 的 `acquire/renew/owns/release` 统一传入 `socket_connect_timeout=5s` 与 `socket_timeout=5s`，配置为 `PYCODE_REDIS_CONNECT_TIMEOUT_SECONDS`、`PYCODE_REDIS_SOCKET_TIMEOUT_SECONDS`。Redis 异常继续映射为 `project_lock_unavailable`，ownership 无法确认继续按 `project_lock_lost` 处理，绝不乐观假定仍持锁。
- Celery Redis broker 使用相同 connect/socket timeout，并显式设置 `broker_connection_timeout`；没有修改 `task_acks_late`、`task_acks_on_failure_or_timeout`、`task_reject_on_worker_lost`、`visibility_timeout` 或 `worker_prefetch_multiplier`。
- PostgreSQL SQLAlchemy runtime engine 对 psycopg 显式传入 `connect_timeout=5s`，配置为 `PYCODE_DB_CONNECT_TIMEOUT_SECONDS`。没有启用全局 `statement_timeout`，也没有增加数据库 transaction retry；commit error 不能被解释为“肯定未提交”并触发业务重跑。
- 现有 `PYCODE_GIT_TIMEOUT_SECONDS=120` 保留，仍约束每个 Git subprocess；没有增加全任务 hard/soft time limit 或 overall wall-clock kill。

## 3. Backend-owned LLM Transport

- 新增 Backend-owned `BackendOpenAIClient` 与 client factory，在 FastAPI/Worker composition 中注入 `PyCodeAdapter`；没有修改受保护的 `pycode/llm_client.py`。
- 显式 transport 默认值为 connect `5s`、read `180s`、write `30s`、pool `30s`、SDK `max_retries=1`，分别由 `PYCODE_LLM_CONNECT_TIMEOUT_SECONDS`、`PYCODE_LLM_READ_TIMEOUT_SECONDS`、`PYCODE_LLM_WRITE_TIMEOUT_SECONDS`、`PYCODE_LLM_POOL_TIMEOUT_SECONDS`、`PYCODE_LLM_MAX_RETRIES` 配置。

- SDK 的有限 request-level retry 不等于 Agent whole-run retry。Backend 没有包裹 `adapter.run_agent()` 的 retry loop，Celery 也没有 `autoretry_for` 或 `self.retry()`。

## 4. Agent Core 持久化 no-retry Boundary

- Alembic revision `20260914_0006`（父 revision `20260914_0005`）为 `agent_runs` 增加 nullable、timezone-aware `core_started_at`；Domain、ORM、Memory/SQLAlchemy Repository、interface 与 GET AgentRun schema 已同步。
- `core_started_at=NULL` 只表示 Backend 尚未 durable 允许 Core 开始；非 NULL 表示必须保守认为 LLM、Tool、Memory、Todo、Task DAG 或模型费用可能已经发生。该 marker 是不可逆历史事实，completed、failed、重复 delivery 或 Worker restart 均不会清除。
- SQLAlchemy `mark_core_started()` 使用条件 `UPDATE ... WHERE id=:id AND status='running' AND core_started_at IS NULL RETURNING ...`；Memory Repository 在 UoW lock 内提供等价语义，并明确区分 `MARKED`、`ALREADY_MARKED`、`INVALID_STATE`、`NOT_FOUND`。
- 真实执行顺序固定为：exact Snapshot checkout → artifact validation → prepare `.pclens` → 验证 BackgroundTask/AgentRun 关联与 running 状态 → persist marker → transaction commit → `adapter.run_agent()`。
- marker commit 失败时 Adapter 调用次数为 0。marker 成功后 Adapter exception、`AgentResult.ok=False`、completed、failed 均保留 timestamp。already-marked 不会被解释为再次进入 Core 的许可。
- 本阶段 pre-core 与 post-core 均没有 automatic whole-task retry；一旦 `core_started_at` 非 NULL，永久禁止 transparent whole-Agent retry。marker commit 后、真正调用 Adapter 前 crash 的保守 false-positive 是有意的 safety policy。

## 5. Repository stage-local Retry

- 新增小型 Backend-owned `run_with_bounded_retry()`，只由明确 whitelist 的 Git network stage 使用：`resolve_remote_branch`（`ls-remote`）、`clone_repository`、`fetch_remote_branch`、`unshallow_repository`。
- 只有上述 operation 抛出结构化 `repository_timeout` 时才 retry；初始调用加最多 1 次 retry，即默认最大 operation attempts 为 2。配置为 `PYCODE_REPOSITORY_OPERATION_MAX_ATTEMPTS=2`、`PYCODE_REPOSITORY_RETRY_BASE_DELAY_SECONDS=1`、`PYCODE_REPOSITORY_RETRY_MAX_DELAY_SECONDS=5`，采用 bounded exponential delay 加至多 25% jitter。
- retry 日志只记录 `project_id`、operation、当前/下一 attempt、`error_code` 与 delay，不记录 Git credential 或 URL secret；测试注入 sleeper/jitter，不真实等待数秒。
- clone timeout 后只删除本次受控 parent 内的 clone staging destination，再重放 clone；不会删除 ready workspace、Snapshot artifact 或其他路径。fetch retry 重放完全相同 command/refspec，不重新选择 branch target。
- `repository_branch_missing`、invalid URL/ref、auth/forbidden（若有可靠 code）、`repository_failed`、`repository_changed`、`repository_commit_unavailable`、`unsafe_repository`、local `rev-parse/ls-tree/update-ref/checkout/clean`、Python Index/Graph 与数据库 transaction 均不 retry。
- 未实现 Artifact rename/publish retry：当前没有足够可靠且跨平台的结构化 temporary sharing-violation 分类，继续使用原 staging/backup/rename/recovery 后 fail 的安全语义。

## 6. 状态机与计数语义

- BackgroundTask 仍严格为 `queued -> running -> completed/failed`；未增加 `retry_waiting`、`retry_scheduled`、`business_retry_at`、attempt table 或 `running -> queued`。
- Repository stage-local retry 全部发生在同一个 running business attempt 内，因此 `attempt_count` 仍只由一次原子 claim 增加为 1。
- stage-local retry 不 publish broker message，因此不改变 5D-4B `enqueue_attempt_count`。Queued Reconciler 仍只扫描 queued、unconfirmed、到期的 publish candidate，不承担 business retry scheduling。
- Celery 未启用 `autoretry_for`、`self.retry()`、soft time limit 或 hard time limit；Windows `solo` 以及未来 Linux Worker 都不会在缺少 Phase 5D-3 recovery 基础时被强制 kill。

# Phase 5D-3 — Worker Failure / Crash Recovery

日期：2026-09-15。状态：实现、真实 PostgreSQL/Redis 并发验证、migration 往返、跨阶段回归和全仓库回归均已完成，等待人工 review。本阶段建立 Worker execution ownership、lease/heartbeat、stale-running reconciliation、Repository exact-target recovery、Agent pre-core 安全恢复与 post-core no-retry，并在全部恢复基础完成后启用 Celery late ACK；Agent Core 保持零修改。

## 1. Durable execution ownership

- Alembic revision `20260915_0007`（parent `20260914_0006`）为 `background_tasks` 增加 nullable `execution_token UUID`、`lease_expires_at timestamptz`、`last_heartbeat_at timestamptz`、`worker_id varchar(255)`，以及 `status='running'` 的 `(lease_expires_at, id)` partial index。
- 每次 PostgreSQL 原子 `queued -> running` claim 生成全新随机 token，以数据库 `now()` 写 heartbeat/lease deadline，记录仅用于观察的 `hostname:pid:celery_request_id`，并只在 claim 时增加 `attempt_count`。
- ownership 条件始终为 `BackgroundTask.id + status='running' + execution_token`；`worker_id` 不参与安全判断。complete/fail、Snapshot binding/activation、Agent marker 和 Agent terminal transaction 都受 token guard。
- terminal task 清除 `lease_expires_at`，保留最后 heartbeat、worker 与 token 供审计；requeue 时清除本次 owner metadata，并保留旧 `attempt_count`。

## 2. Heartbeat and ownership-loss behavior

- Worker claim 成功后启动 Backend-owned heartbeat coordinator；每次 heartbeat 打开独立短生命周期 SQLAlchemy Session/transaction，不与业务线程共享 Session。默认 TTL `420s`、heartbeat `30s`、scanner `30s`。
- conditional heartbeat 返回 0 row 表示明确失去 ownership；数据库临时不可用表示 ownership unknown。correctness boundary 无法确认 ownership 时停止进入新 stage/publish/activation/terminal write，并由 Celery adapter `Reject(requeue=True)`，保留 running lease 交给 scanner。
- duplicate delivery 的 `ALREADY_RUNNING/TERMINAL` 路径不启动 heartbeat。stale owner 的 complete/fail、Agent Trace/result 和 Repository activation 均被拒绝。
- DB lease 配置在 Worker composition 中校验：必须大于 Redis Project lock TTL 加至少一个 heartbeat/scanner scheduling interval；默认 `420 > 300 + 30`。

## 3. Repository durable target and exact recovery

- 正常 Index 在 remote revision 已确定且 Snapshot resolve/create-get 后，立即在同一 owner-guarded transaction 将 `BackgroundTask.snapshot_id` 绑定到目标 Snapshot；之后才进入 checkout/build/publish/activate。
- stale task 在 target 未绑定时保守失败为 `worker_execution_lost`，不会重新 synchronize 或重新选择 remote HEAD。
- 已绑定且仍为安全 `indexing` 状态、Project current 未冲突、`attempt_count < 2` 时转回同一 task ID 的 queued；新 claim 使用同一 `snapshot_id` 和 `Snapshot.commit_sha`，只做本地 commit availability、exact checkout、published artifact recovery/同 Commit rebuild，不调用 `synchronize()`。
- Snapshot 已 ready 且 Project ready/current 指向它时只补齐 BackgroundTask completed；Snapshot failed、ready/current mismatch、Project current 指向其他 Snapshot 或 attempt budget 用尽时保守失败，不复活不安全状态。
- DB execution ownership 与 Redis Project lock 分工不变：前者 fence 数据库 owner/write，后者保证 Project workspace single writer；关键文件系统边界同时检查两者。

## 4. Agent pre-core and post-core policy

- pre-core 自动 requeue 仅在关联 Project/Snapshot/AgentRun 全部有效且 ready/current 一致、AgentRun running、`core_started_at IS NULL`、result/finished_at/Trace 均为空、token 非空、`attempt_count < 2`、并能取得 Project lock 时成立；BackgroundTask 与 AgentRun 在同一 transaction 一起回到 queued。
- `core_started_at IS NOT NULL` 是不可逆 no-retry boundary。stale scanner 将 BackgroundTask 与仍 running 的 AgentRun 标为 failed，BackgroundTask 使用 `worker_lost_after_agent_core`；recovery path 不依赖也不调用 adapter/Core。
- Agent marker transaction、success/failure terminal transaction 都先锁定并校验 BackgroundTask owner，再写 marker、Trace、result 和两条 terminal 状态。旧 Worker 的 fake Core 即使稍后返回，也不能新增 Trace、覆盖 result 或覆盖新 terminal 状态。
- confirmed queued delivery 的永久关联一致性错误不再因 claim transaction rollback 回到 queued：claim 先提交，随后 owner-guarded terminalize；数据库基础设施故障则不伪造永久结果，走 reject + lease reconciliation。

## 5. StaleRunningReconciler and 5D-4B handoff

- 新增独立 `StaleRunningReconciler` 与 Celery task `pycode.tasks.reconcile_stale_running`；Beat 默认每 `30s` 调用，batch 默认 `100`。候选为 running 且 lease 早于 PostgreSQL `now()`；legacy running NULL token/lease 也进入保守 reconciliation。
- 并发保护使用 token/expired-lease conditional UPDATE RETURNING，并在 Agent marker/requeue 路径统一采用 BackgroundTask-first row lock order。heartbeat/scanner、scanner/scanner、terminal/scanner、marker/scanner 只能有一个有效 transition。
- Project task 在决策前尝试获取统一 Redis project lock；仍 busy/unavailable 时 defer。scanner 只在 reconciliation transaction 外围暂持自己的 compare-token lock，完成后立即释放，绝不转交给新 Worker。
- stale `running -> queued` 只清除 `enqueue_confirmed_at` 并把 `next_enqueue_attempt_at` 置为 DB now；scanner 不直接 publish、不增加 `enqueue_attempt_count`。5D-4B `QueuedTaskReconciler` 后续 reserve 并 publish 同一 task ID，实际 publish attempt 时才增加 enqueue counter。

## 6. Celery delivery settings

- 在 lease/scanner/fencing 完成后启用 `task_acks_late=True`、`task_acks_on_failure_or_timeout=True`、`task_reject_on_worker_lost=True`、`worker_prefetch_multiplier=1`。
- Redis broker transport 显式设置 `visibility_timeout=21600`，可通过 `PYCODE_CELERY_VISIBILITY_TIMEOUT_SECONDS` 调整；它不是业务 operation timeout。Celery result backend 继续 disabled。
- 基础设施数据库失败由 health/index/Agent 三个 task adapter 显式 `Reject(requeue=True)`；永久业务/一致性失败先持久化 terminal 状态后抛出，由 `task_acks_on_failure_or_timeout=True` ACK，不会形成无限 redelivery。

## 2. v1 设计冻结与分层

讨论过终态批量持久化和运行中增量持久化，v1 最终选择前者：`Agent Core → 内存 Internal Trace/ToolTrace → AgentResult → Backend ApplicationTraceNormalizer → Application Events → 终态事务 → trace_events → Query API`。这样保留 Core/Backend 解耦及 Phase 5 已有 owner-guarded terminal transaction，不引入 per-event sequence、幂等和 fencing 机制；Worker crash 丢失 partial Core Trace 是明确接受的 v1 限制，用 `trace_complete=false` 表示。

Internal Trace 继续供 Core 调试、内部测试、CLI/debug 和 normalizer 使用；Application Trace 是 Backend/API 的稳定版本化契约。不能把 `PreToolUse`、`TurnStarted`、`LLMNextActionSchemaFailed` 等内部名称直接公开。v1 仅有 9 种 Public Event：`run_started`、`plan_created`、`context_updated`、`llm_started`、`llm_finished`、`tool_started`、`tool_finished`、`run_completed`、`run_failed`。它们不是固定工作流：未发生计划、LLM 或工具调用，就不伪造相应事件；Turn、Todo、Policy、Observation、Memory outcome 不设独立 Public Event。

`backend/app/core/application_trace.py` 集中定义 `ApplicationEventType`、`ApplicationTraceEvent`、LLM purpose、error category、failure stage 和 payload validation。Envelope 固定为 `schema_version=1`、每个 Run 从 0 连续递增的 `sequence`、上述 9 种 `event_type`、timezone-aware 且 API 统一 UTC 的实际事件时间 `occurred_at`、始终存在的 `tool_name`、按类型验证的 JSON object `payload`。仅 tool events 可使用非空 `tool_name`，其它固定为 null。Normalizer 在筛选后重新编号；`run_started` 为 sequence 0。数据库 `created_at` 只表示持久化时间，不能代替 `occurred_at`。

## 3. Application Event Contract 与来源

| Public Event | 实际来源与主要 payload |
| --- | --- |
| `run_started` | Backend `AgentRun.started_at`；`run_type`、`snapshot_id`，不复制 task。 |
| `plan_created` | `LLMPlanGenerated → llm/false`，`LLMPlanFallback → fallback/true`，`PlannerSelected → rule/false`；`steps` 取权威 `AgentResult.steps`，`step_index` 从 0 生成。 |
| `context_updated` | 完整 Internal section identifiers 映射到固定 Public identifiers；必填 `included_sections`，可含 `turn_index/skipped_sections/warnings`。 |
| `llm_started` | 实际 LLM operation 开始；purpose 仅 `plan`、`next_action`、`summary`、`memory_selection`、`memory_extraction`。 |
| `llm_finished` | 同一 operation 的完成；必填 `purpose/success/fallback_used`；失败必有 Public error，schema parse failure 也算失败，fallback 仅指本次 operation。 |
| `tool_started` | `PreToolUse` 作顺序锚点；ToolTrace 提供开始时间、turn、经脱敏的 arguments；reason 来自匹配的决策。 |
| `tool_finished` | `PostToolUse` 作顺序锚点；ToolTrace 的 `ok/failed/denied → success/failed/denied`，可含 duration、summary、error、`denied_by=policy/hook/other`，不公开 `result_data`。 |
| `run_completed` | 仅 Backend `AgentRun.status=completed`；`stop_reason/has_result/trace_complete`，可含 Run duration。summary LLM 失败而现有 AgentResult 仍 completed 时允许 `has_result=false`。 |
| `run_failed` | 仅 Backend `AgentRun.status=failed`；`stage/error/trace_complete`，可含 Run duration。stage 仅从明确 failure boundary 取 `planning/context/llm/tool/summary/agent_core/backend`，不按异常字符串猜测。 |

Public Context identifier 固定为 `system/project/plan/tool_results/evidence/task_state/memory/execution_history`。显式映射：`identity/tools/policy/response_contract → system`，`tasks/todo → task_state`，`memory/memory_index → memory`，`trace → execution_history`；其余 `project/plan/tool_results/evidence` 同名映射。未知 Internal section 忽略；输出使用固定 Public 顺序，不公开 Internal ordering、source、placement、priority、size_estimate、section content 或 skipped reason。

Public error 统一为必填 `category`、可选 `code/message`。12 种 category 为 `configuration/authentication/rate_limit/timeout/invalid_response/schema_validation/policy_denied/tool_error/agent_error/backend_error/worker_lost/unknown`；显式 mapper 无法稳定分类时使用 `unknown`。message 仅取安全 catalog 或经 sanitizer 处理的内容，不公开 traceback、API key、Authorization header、完整 provider response/prompt、raw LLM response 或任意原始异常字符串。

## 4. Core 纯 instrumentation 与 Backend normalizer

Phase 6 首次允许对 Agent Core 做纯观测改动，但不改变 Agent 决策行为。`pycode/agent/trace.py::TraceRecorder` 增加 Internal `LLMCallStarted` / `LLMCallFinished`；`pycode/agent/runtime.py` 和 `pycode/agent/memory.py` 在 plan、next-action、summary、memory-selection、memory-extraction 的实际调用边界附近记录 started/finished、success/failure、fallback 和安全分类。没有改变 prompt、模型选择、LLM/Tool 调用次数、retry、fallback、返回值、异常传播、stop condition 或 AgentResult。

原 `ContextAssembled` 的 `sections` list 受 debug summarizer 8 项上限影响。`pycode/agent/runtime.py::_record_context_event` 因此额外记录完整、紧凑、未截断的 `included_section_names` / `skipped_section_names`；仅增加 identifier 观测，不改 Context builder、内容、顺序、Prompt 或 included/skipped 判定。

正式 `ApplicationTraceNormalizer` 实现在 `backend/app/core/application_trace.py`，由 `backend/app/integrations/agent_trace.py` 暴露给服务层。它合并 AgentRun durable state、AgentResult、AgentTrace/Internal Events、ToolTrace 和 Backend failure context，完成 lifecycle synthesis、LLM/context/tool projection、error normalization、sanitization、schema validation、sequence 重编号和 `trace_complete` 判断。旧 `map_agent_trace()` 直接持久化 Internal Events 的路径已被替换。

ToolTrace 是工具 payload、时间和结果的权威；`PreToolUse/PostToolUse` 仅是 timeline anchor，当前按 `(turn_index, tool_name)` 匹配，不为同一次调用重复产生两套 Public events。冲突时依次参考 ToolTrace、PolicyDecision、Pre/Post、NextActionDecided、ObservationRecorded；匹配不可靠时不静默伪造。集中 sanitizer 递归遮蔽 `token/secret/password/authorization/api_key/apikey/access_key`，限制字符串、list、object 深度/数量和总 payload 大小；arguments 不能安全输出时省略，隐私与正确性优先于丰富度。

`trace_complete` 与 Run status 独立：完整 Core 返回且关键 Application projection 无丢失为 true；post-Core crash、无 AgentTrace 的 Core/Adapter exception、lifecycle-only Trace 或关键 normalization 降级为 false。unknown Internal Event 忽略；缺失或不安全的可选字段省略；无法可靠归一化的关键非 lifecycle event 跳过并置 false；malformed Application Event 不入库。整个 normalizer 异常时尝试从 durable AgentRun 生成 lifecycle-only fallback，再失败则放弃 Trace，不将原本成功的 Run 改成 failed。数据库不可用和 ownership 无法确认仍按 Phase 5 规则处理，不属于 normalizer degradation。

# Phase 7 — SSE 实时 Agent Trace

日期：2026-09-16。状态：设计冻结、实现、自动化回归、真实 Redis/SSE 人工 E2E 与 Worker hard-crash 验收均已完成；**Phase 7 v1 Final Acceptance：PASS**。本阶段让客户端在 Agent 仍执行时收到结构化 Application Trace，同时继续由 PostgreSQL 保存终态历史。Phase 6 的 9 种 Application Event 和 `GET /api/v1/agent-runs/{run_id}/trace` 保持原契约；Redis Stream 只承载临时实时传输。

## 1. 开发前审计与目标

只读 Current-State Audit 的结论为 **READY FOR PHASE 7 DESIGN**。原链路是 `Agent Core → Internal Trace/ToolTrace → AgentResult → ApplicationTraceNormalizer → PostgreSQL`，完整 Public projection 只在 Core 返回后进行。`TraceRecorder` 原无 callback、listener、observer 或 sink；Core 已有 plan 确定、Context assembled、LLM start/finish 和 ToolTrace start/finish 等观测边界。仅监听 `record_event()` 不够：plan 的完整 steps、Context 后补的紧凑 included/skipped identifiers 和 ToolTrace 的最终状态需要在各自完成后观察。

Phase 6 已冻结 `schema_version=1` 的 `run_started/plan_created/context_updated/llm_started/llm_finished/tool_started/tool_finished/run_completed/run_failed` 九种事件及 `sequence/occurred_at/tool_name/payload` envelope。Phase 7 复用该 Public Contract，不引入第二套事件分类。`REDIS_URL`、redis-py、Celery broker、Project Lock 与 Starlette `StreamingResponse` 已存在；多客户端完整可见性采用每个连接自己的 `XRANGE` 历史回放和 `XREAD` 实时跟随，不使用 Consumer Group。PostgreSQL 仍是 durable historical source of truth。

## 2. Design Review、三个 blocker 与最终冻结

第一次 **Phase 7 v1 Realtime Trace Design Review** 结论为 **NOT READY FOR DESIGN FREEZE**，指出三个 correctness blocker：

1. 若在首次 `mark_running` 后发布 `run_started`，Phase 5 允许的 pre-Core safe requeue 会留下旧 attempt 的公开 sequence 0。最终改为准备完成并成功提交 `mark_core_started` 后才激活 realtime session；`run_started.occurred_at` 仍取有效 attempt 的 `AgentRun.started_at`。Core 前无 Stream、无 Public Event 是正常状态，新 attempt 从 sequence 0 开始。
2. `run_completed/run_failed` 依赖最终 status、`finished_at`、result/error 和 `trace_complete`。最终改为先在 owner-guarded 事务中更新 AgentRun，再构造终态 Event、持久化 session buffer 和更新 BackgroundTask；事务提交成功后才尽力发布终态 Redis Event。
3. Worker crash 后 Redis partial timeline 与 PostgreSQL lifecycle-only timeline 可能同 sequence、不同内容。最终要求跨来源续传前比较 `Redis[0..N]` 与 `PostgreSQL[0..N]` 的六个公开字段，不能只比较数字 sequence；无法证明连续性时报告 `realtime_trace_gap`。

第二次 **Phase 7 v1 Final Design Freeze Verification** 对上述三个 blocker 的结论为 **READY FOR DESIGN FREEZE**。冻结范围还明确：投影失败跳过候选且不占 sequence，并令 `trace_complete=false`；Redis 发布失败只降低实时传输，不改变已生成 Event、业务终态或 `trace_complete`；客户端断开不取消 Agent。

## 3. RealtimeTraceSession 与 Core 纯观察接入

`backend/app/core/realtime_trace.py` 实现 Backend-owned、per-attempt `RealtimeTraceSession`。成功提交 Core marker 后，它用有效 `AgentRun.started_at` 生成并缓冲 `run_started`（sequence 0）。随后 observation 当场投影为通过 v1 校验的 `ApplicationTraceEvent`，按 `len(buffer)` 分配连续 sequence；同一个 Event 对象进入内存 buffer，尽力发布到 Redis，并在正常终态由原 buffer 原 sequence 写入 `trace_events`。普通运行不在终态重新生成 plan、Context、LLM 或 Tool Event。Phase 6 的 plan/context/tool builder、sanitizer、public error mapping 和 payload validator 被实时投影复用；无完整结果、Core 异常或终态投影失败时保留 lifecycle-only fallback。

Core 仅增加 optional observer seam：`pycode/agent/trace.py` 的 `TraceRecorder` 在 LLM start/finish、ToolTrace start/finish 和决策 reason 完成后通知；`pycode/agent/runtime.py` 在完整 plan steps 确定、Context compact identifiers 写齐后通知。`pycode/agent/executor.py`、`pycode/engine.py` 与 `backend/app/integrations/pycode.py` 只透传可选 observer；Backend service 在适配器支持该参数时传入 session callback。Core observer 异常被隔离，不改变 planner、prompt、LLM/Tool 调用次数、fallback、retry、Memory、Todo、stop condition 或 AgentResult。Core 不依赖 Redis、FastAPI、SSE、PostgreSQL 或 BackgroundTask。

`AgentRunService` 在 `mark_core_started` durable commit 前不创建 session。每次非终态 Redis 发布前调用既有 `ExecutionOwnership.ensure_owned()`；确认 ownership lost 后不再发布后续实时 Event。projection/validation 失败的候选不进 buffer、不占 sequence，并将 session 标记 degraded；终态 `trace_complete=false`。Redis XADD 失败则保留 buffer，终态 PostgreSQL 仍可持久化，`trace_complete` 不因此变 false。终态 Event 在 owner-guarded AgentRun 更新之后构造，随 buffer 写入同一事务；提交后发布终态时不再要求 BackgroundTask 仍处于 running。终态投影本身异常也走 lifecycle-only 降级，不改变已成功的业务完成。

## 4. Redis Stream 与 SSE 服务

`backend/app/infrastructure/realtime_trace.py` 使用每 Run 一个 `pycode:agent-runs:{run_id}:events` Stream。Worker 使用独立的同步 Redis publisher，通过 transactional pipeline 一起执行 `XADD MAXLEN ~ 512` 与 `EXPIRE 86400`；`backend/app/infrastructure/redis.py` 和 `.env.example` 提供 stream 长度、TTL 与 SSE 连接池上限配置，继续复用 `REDIS_URL`。该 client 不与 Project Lock client 共享。Worker composition 在 `backend/app/tasks/runtime.py` 注入 publisher；FastAPI 在应用状态中按需建立有连接数上限的 `redis.asyncio` client，并在 lifespan 结束时关闭。

`backend/app/api/agent_runs.py` 注册 `GET /api/v1/agent-runs/{run_id}/events`，具体实现位于 `backend/app/api/realtime_trace.py`，使用 Starlette `StreamingResponse`。普通帧为 `id: <Application sequence>`、`event: trace`、`data: <v1 ApplicationTraceEvent JSON>`；Redis Stream ID 只作内部 cursor。运行中首次连接从 `XRANGE` replay 后以独立 `XREAD` cursor 跟随，mid-run 加入和多个客户端都可取得完整可用历史。`Last-Event-ID: N` 只发送 sequence 大于 N 的 Event；终态无该 Header 时直接从 PostgreSQL 回放并关闭，既有 `/trace` 继续只读 PostgreSQL。

Stream 裁剪、跳号或无法证明续传时，响应头发送前返回 HTTP 409 `realtime_trace_gap`；已建流时发送不带 `id` 的 transport control frame `event: realtime_trace_gap` 并关闭。运行所需 Redis 在建流前不可用时返回 HTTP 503 `realtime_trace_unavailable`。终态带 `Last-Event-ID` 时，按 `schema_version/sequence/event_type/occurred_at/tool_name/payload` 的规范化值验证 Redis 与 PostgreSQL 的 0..N 前缀，成功才从 PostgreSQL 补发 N 之后的事件；活动连接也在有限 `XREAD` 等待后检查终态，以处理终态 XADD 失败。约 5 秒的有限 blocking read、约 15 秒的 `: ping`、`request.is_disconnected()` 与 generator cancellation 负责连接存活和断开；heartbeat、gap 控制帧都不进入 Application sequence、Redis buffer 或 PostgreSQL。

## 5. Phase 5/6 兼容与异常语义

Phase 5 pre-Core safe retry 不会遗留旧 attempt 的 `run_started` 或 Redis Stream Event；`mark_running` 到 `mark_core_started` 之间可以连接 `/events` 并等待，但没有 Application Event。Phase 6 `/trace` 对 queued/running、终态、legacy row 的查询语义未改为读取 Redis。正常路径中 Redis、buffer、PostgreSQL 可保存相同事件值；Redis 发布失败、裁剪/过期、projection 降级或 Worker crash 时不承诺跨系统一致。Browser disconnect、Stream expiry、XADD failure 和 SSE 网络错误本身不改变 `trace_complete`。

post-Core hard crash 后，Redis 可以保留已观察到的 partial realtime history，而 PostgreSQL 在 stale reconciliation 后只保存 `run_started + run_failed`、`trace_complete=false`。Core marker 非空继续禁止透明重跑；执行 token 和 owner guard 继续阻止旧 owner 写业务终态。此时客户端带旧 `Last-Event-ID` 重连，前缀若已分叉就返回 `realtime_trace_gap`，应重新读取 durable `/trace`，不能把两个 timeline 拼成虚假的连续历史。

Phase 7 没有 database migration、新第三方依赖或 frontend。Alembic `current` 与唯一 `heads` 仍为 `20260915_0007`。本次实现涉及上述 Backend Core、service、API、runtime、Redis infrastructure、Core observer 透传，以及 `tests/backend/test_realtime_trace.py`、现有 Agent/API 测试和 Redis 配置样例；`.gitignore` 的 `.tmp/` 规则仅忽略测试临时目录。Celery Beat schedule 文件及 `.tmp` 内文件是运行时/测试状态，不属于 Phase 7 功能交付。

## 8. Bug：Todo / Step Binding

真实 Agent E2E 暴露错误 `Completed todo cannot move to in_progress`。根因不是 SSE：Agent runtime 原来只按已执行 Tool 轮数和 `tool_name` 重新匹配 Plan Step，没有排除已经 `COMPLETED` 的 Todo；同名工具、乱序工具或 `todo_write` 提前完成 Step 时，可能再次尝试 `COMPLETED → IN_PROGRESS`。TodoManager 正确拒绝了这个非法状态转换，Trace/SSE 只是让原有 Core 问题更容易被观察。

修复保留 TodoManager 状态机约束，不允许 completed Todo 重新进入 in-progress。Step resolution 先保持原计划顺序偏好，再跳过 completed Todo，同名工具可绑定下一条仍可执行 Step；新参数的计划外调用继续使用原有 unbound semantics。执行入口 `_start_step_todo` 增加 defense-in-depth 检查，`todo_write` 提前完成的 Step 也不能再次启动。修复没有修改 Planner response schema，也没有向 LLM contract 增加 `todo_id`。新增回归覆盖同名 Step、乱序 Step、重复已完成调用、计划外调用和入口防线。

# Phase 9 — Docker 与工程化

日期：2026-09-20。状态：Docker / Engineering 实现、镜像构建、完整自动化测试、Compose 基础设施冒烟与持久化复验均已完成；**Phase 9 Implementation Acceptance：PASS**。这是 PyCode V2.0 最后一个主开发阶段，目标是把“需要多个本地终端和手动基础设施配置”升级为可通过 `docker compose up --build` 稳定启动和复现的完整系统，同时不破坏 Windows Local Development。

当前仓库事实说明：`HEAD=6241bd8`，Phase 9 文件在 working tree 中存在并已实际验证，但当前 `git log --all` 没有 Phase 9 commit。由于本轮禁止 commit，本记录只记载实现与验收事实，不虚构提交 ID；提交归档状态见第 21 节。

## 1. Current-State Audit

容器化前需要分别启动 FastAPI、Celery Worker、Celery Beat、Vite、PostgreSQL 与 Redis。Audit 确认了以下工程约束：

- Backend 和 Worker 都访问受管理 Repository Workspace；数据库持久化的是绝对 `workspace_path`，两个容器必须在完全相同的绝对路径挂载同一 Workspace；
- Frontend production 应由 Nginx 提供静态文件，而不是运行 Vite dev server；
- SSE 经 Nginx 时必须关闭 buffering/cache，并保留长连接 timeout；
- Migration 不能由 Backend、Worker、Beat 并发执行；
- Celery Beat 默认 schedule file 不应写入 `/app` source tree；
- Windows Local data 中的绝对路径不能直接用于 Linux container，Local 与 Docker 应默认隔离。

## 2. Docker Runtime Topology

最终 Compose 固定七个 service：`postgres`、`redis`、一次性 `migrate`、`backend`、`worker`、`beat`、`frontend`。Backend、Worker、Beat 和 migrate 复用 `pycode-backend:phase9` Python image；Frontend 使用 Node build stage 产出静态资源，再由 `pycode-frontend:phase9` 的 Nginx runtime 提供服务。没有增加独立 gateway、Flower、Prometheus、Grafana、ELK/Loki 或私有 Git service。

## 3. Backend Dockerfile

`backend/Dockerfile` 基于 `python:3.12-slim`，只额外安装 runtime 所需的 `git` 与 `ca-certificates`，复制 Python package、Backend、Alembic 配置并使用现有 `pyproject.toml` 的 `[backend]` extra 安装依赖。默认 API command 为：

```text
python -m uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```

Linux Worker 使用 `python -m celery -A backend.app.worker:app worker --loglevel=INFO`，不带 Windows Local Mode 所需的 `--pool=solo`。Beat 使用同一 image，执行 `python -m celery -A backend.app.worker:app beat --loglevel=INFO --schedule=/tmp/celerybeat-schedule`，schedule metadata 不写项目根目录，也不挂载持久化 volume。

## 4. Frontend Dockerfile

`frontend/Dockerfile` 是 multi-stage build。第一阶段固定 `node:24.15-alpine`，先复制 package/lock file 执行 `npm ci`，再执行 `npm run build` 生成 `/app/dist`；`VITE_API_BASE_URL` 明确保持空字符串以使用同源 API。第二阶段基于 `nginx:alpine`，只复制 Nginx 配置和 `dist/`。生产容器不执行 `npm run dev`。

## 5. Nginx 与 SPA Routing

`frontend/nginx.conf` 使用 `try_files $uri $uri/ /index.html`，因此 `/projects/new`、`/projects/:id`、`/projects/:id/history` 和 `/projects/:id/graph` 直接访问或刷新不会返回 Nginx 404。`/api/` 原样代理到 `http://backend:8000`，Browser 始终请求同源路径，不需要解析 Docker internal hostname，也避免生产 CORS 配置。

## 6. SSE Through Nginx

实时链路为 `Browser → Nginx → FastAPI StreamingResponse → Redis Stream`。Nginx 配置 `proxy_http_version 1.1`、空 `Connection` header、`proxy_buffering off`、`proxy_cache off`、`proxy_read_timeout 3600s` 和 `gzip off`。这些设置防止 Phase 7 的实时 Trace 被代理层聚合成“Agent 结束后一次性返回”；Backend SSE contract 本身没有修改。

## 7. Shared Workspace Volume

命名卷 `pycode_workspace` 在 Backend 与 Worker 中都挂载为 `/var/lib/pycode/workspaces`，两者都注入 `PYCODE_WORKSPACE_ROOT=/var/lib/pycode/workspaces`。这是 correctness 条件，不只是部署便利：若数据库中的 `workspace_path` 与某个容器的实际路径不一致，会导致 `workspace_unavailable`，或使 Snapshot / Artifact 对 Worker 不可见。Beat、migrate 和 frontend 不挂载 Workspace。

## 8. Persistence

Compose 定义三个命名卷：

- `postgres_data`：PostgreSQL 业务事实源；
- `redis_data`：Redis AOF，降低 queued message、broker state、realtime Stream 与短期协调状态在 container restart 时的中断，但 Redis 仍不是业务事实源；
- `pycode_workspace`：保存 Repository clone、`.git`、Snapshot Artifact、index、graph、Agent Memory 与 Task state。

`docker compose down` 删除 container/network 但保留 volumes；再次 `up` 可恢复数据。`docker compose down -v` 才删除 Docker PostgreSQL、Redis 与 Workspace 数据，不作为日常操作，也不承诺 `down -v` 后保留数据。

## 9. Database Migration

Migration 由独立一次性 `migrate` service 唯一执行：`PostgreSQL healthy → python -m alembic upgrade head → Exited (0) → backend/worker/beat start`。后三个长期服务均依赖 `service_completed_successfully`。这样避免多个进程并发运行 Alembic，也使 migration failure 明确阻止业务服务启动，而不是被 restart loop 掩盖。

## 10. Health Checks

- PostgreSQL：`pg_isready`；
- Redis：`redis-cli ping`；
- Backend：Python stdlib 请求 `GET /health`，不为此安装 curl；
- Frontend：Nginx image 内置 `wget` 请求 `/`；
- Worker：不配置容易受 node identity 影响的伪 healthcheck，验收时使用 `celery inspect ping`；
- Beat：没有不存在的业务 health API，通过 process state、restart policy 和 schedule logs 验证。

长期服务统一 `restart: unless-stopped`；migrate 不进入长期 restart loop。

## 11. Environment Strategy

根目录 `.env` 不会 COPY 进 image；`.dockerignore` 同时排除 `.env` 与 `.env.*`，仅保留无 secret 的 `.env.example`。Backend 系列 service 通过同一个 `env_file` 接收 LLM、timeout、retry、lease、realtime 等配置，Compose 再覆盖 Docker 专用值：

```text
DATABASE_URL=...@postgres:5432/...
REDIS_URL=redis://redis:6379/0
PYCODE_WORKSPACE_ROOT=/var/lib/pycode/workspaces
```

因此 container 使用 `postgres` / `redis` service DNS，而 Local Development 的 `.env` 仍可继续使用 `127.0.0.1`。`OPENAI_API_KEY`、`OPENAI_MODEL`、`OPENAI_BASE_URL`、`OPENAI_API_TYPE` 等只通过环境变量提供，不写入 Dockerfile、Compose、Frontend build 或开发记录。

## 12. Local Mode vs Docker Mode

PyCode V2.0 保留两种并存运行方式：

- **Local Development**：本机 venv、FastAPI、Windows `--pool=solo` Worker、独立 Beat、Vite、本机 PostgreSQL/Redis，适合开发和调试；
- **Docker Compose**：`docker compose up --build` 启动完整系统，适合稳定运行、演示、复现和 E2E。

两套模式默认使用不同数据库和 Workspace。现有 Windows 数据库中的 `F:\...` 绝对 `workspace_path` 不能直接用于 Linux `/var/lib/pycode/workspaces/...`；Phase 9 不实现 Windows DB/Workspace 到 Docker 的自动迁移。

## 13. Docker Model Configuration 与 Operational Note

日常更换模型或 provider 时修改根目录 `.env` 中的 `OPENAI_API_KEY`、`OPENAI_MODEL`、`OPENAI_BASE_URL` 与 `OPENAI_API_TYPE`，再执行：

```powershell
docker compose up -d --force-recreate backend worker
```

Repository Question / Impact 使用 Backend 的 LLM config，Agent Task 使用 Worker 的 LLM config，因此两者都需 recreate。实际操作中 Backend recreate 后，旧 Nginx process 可能仍缓存原 Backend container IP 并短暂返回 502；执行 `docker compose restart frontend` 使 Nginx 重新解析 `backend` service。这是 Docker operational note，不是业务逻辑 Bug。

# PyCode V2.0 Final Architecture

```text
Browser
  ↓
Nginx / React
  ↓
FastAPI ─────→ PostgreSQL
  │            Redis / SSE Streams
  │            Shared Workspace ←──── Celery Worker
  ↓                                  ↑
Redis Queue ─────────────────────────┘

Celery Beat
  ↓
Queued / Stale-running Reconciliation

Agent Core
  ↓
Repository / Snapshot / Artifact
  ↓
LLM / Tools
```

- **Frontend**：React + TypeScript + Vite；Nginx 提供 production static files、SPA fallback、同源 API 与 SSE proxy。
- **Backend**：FastAPI 提供 Project、Snapshot、Graph、Analysis、AgentRun、Trace 与 SSE API，Application Service 保持业务边界。
- **Persistence**：PostgreSQL 保存业务事实；Redis 承担 Celery broker、Project lock、realtime Stream 与短期协调；Shared Workspace 保存 Repository 与 Snapshot Artifact。
- **Async execution**：Celery Worker 执行 Repository Index 和 Agent Task；Beat 驱动 queued orphan 与 stale-running reconciliation；execution token、lease、heartbeat 与 no-retry boundary 保持 Phase 5 correctness。
- **Snapshot lifecycle**：Project 指向 current ready Snapshot；分析与 AgentRun 固定 exact commit / exact Artifact，不回退到 mutable remote HEAD。
- **Trace / Realtime**：PostgreSQL 保存 durable versioned Application Trace；Redis Stream + SSE 提供 best-effort realtime timeline，并用 gap semantics 防止拼接分叉历史。
- **Agent**：PyCode Core 保持可独立调用，Backend adapter 负责 LLM transport、workspace、persistence 与 runtime integration。
- **Docker / CI**：Compose 复现七服务运行拓扑；Basic CI 分别验证 Python、Frontend 与 Docker build/config，不调用付费 LLM。
