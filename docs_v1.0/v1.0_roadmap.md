# PyCode V1.0 Roadmap

> 创建日期：2026-07-09  
> 目标版本：V1.0  
> 依据材料：`develop_requirements.md`、demo 版实现现状、`CCLearning NO.1-6` 学习笔记

## 1. V1.0 目标

V1.0 的核心目标不是继续堆 demo 功能，而是把 PyCode 从“能展示的代码库理解 Agent demo”升级为“结构稳定、边界清楚、可观测、可恢复、可继续扩展的 Agent harness 工程底座”。

一句话目标：

```text
让 PyCode 成为一个面向 Python 代码库理解与开发分析任务的轻量 Agent harness。
```

V1.0 需要达成的效果：

1. 稳定的 Agent 主循环
   - 将当前偏 `plan-and-execute` 的 runtime，升级为更接近 `observe-decide-act` 的 Agent loop。
   - 明确 user task -> build context -> decide next action -> execute tool -> observe result -> decide continue/stop -> answer 的完整链路。
   - planner 的核心职责从“一次性生成完整步骤列表”，升级为“基于当前状态决定下一步该做什么”。
   - 明确 runtime、planner、executor、policy、tools、trace、memory、context 的职责边界。
   - 支持离线规则 planner 与 LLM planner 的稳定切换。

2. 稳定的工具调用生命周期
   - 工具调用前有参数校验和权限检查。
   - 工具调用中有统一输入、输出、错误、摘要和结构化数据格式。
   - 工具调用后有 trace、evidence、todo 状态更新和 context 注入。
   - 工具失败不直接破坏整个 Agent run，而是进入可解释的失败状态。

3. 清晰的权限与安全边界
   - 默认只读分析，不自动修改代码，不自动提交 git。
   - 测试运行、文件写入、危险命令等能力必须显式受控。
   - 路径访问必须限制在目标项目目录或允许目录内。
   - 权限拒绝也必须进入 trace，而不是静默失败。

4. 可观测 Agent 内核
   - 每次 Agent run 都能输出结构化 trace。
   - 每个 loop turn、next action 和 tool result 都能被记录。
   - todo 能反映当前 loop 中已经完成、正在执行和仍需继续的事项。
   - evidence 能追溯到文件、图谱关系、工具输出或记忆来源。
   - CLI / Web UI 可以展示计划、工具调用、错误、证据和最终结论。

5. 可恢复的任务与记忆系统
   - Memory 用于保存项目级知识，而不是保存所有聊天内容。
   - Task DAG 用于表达跨会话任务依赖，而不是替代项目管理软件。
   - 记忆和任务都要能被 CLI 查询、被 Agent 按需注入、被用户审查。

6. 分层 Context / Prompt 组装
   - 统一由 context builder 管理 Agent 可见信息。
   - identity、tools、policy、project、retrieval、trace、todo、tasks、memory、evidence 分层组装。
   - 不存在的数据不注入。
   - 阶段三问答 prompt 与 Agent prompt 保持边界清楚。

7. 面向真实开发分析场景可用
   - 入口分析。
   - 新手阅读顺序。
   - 改动影响分析。
   - git diff 风险分析。
   - 测试覆盖检查。
   - 工具调用过程解释。
   - Agent run 报告或可复制摘要。

V1.0 最关键的架构变化：

```text
当前 demo 版：
user task
-> planner 一次性生成 steps
-> executor 顺序执行 steps
-> runtime 汇总
-> answer

V1.0 目标：
user task
-> runtime 初始化状态
-> loop turn 1: build context -> planner decide next action -> act -> observe
-> loop turn 2: build context -> planner decide next action -> act -> observe
-> ...
-> planner decide final_answer / stop
-> runtime 汇总 answer
```

因此，V1.0 中 planner 的关键变化是：

```text
从：根据用户任务生成完整计划
到：根据当前状态决定下一步该干什么
```

阶段边界需要特别明确：

```text
V1.0-A：
先完成 observe-decide-act loop 的工程结构。
next-action 决策先使用规则 planner。
LLM 仍可用于初始计划和最终总结，但不负责每一轮是否继续、下一步调什么工具。

V1.0-C：
必须完善 LLM-driven loop。
LLM next-action planner 要基于当前 context / evidence / trace / todo / tool results 决定：
1. 下一步是否调用工具；
2. 调用哪个工具和参数；
3. 证据是否已经足够；
4. 是否输出 final_answer；
5. 是否 stop_with_error。
```

## 2. 非目标

V1.0 不追求复刻完整 Claude Code / Codex，也不把 PyCode 做成通用多 Agent 平台。V1.0 的非目标如下：

1. 不做完整自动代码修改器
   - Agent 默认不自动改代码。
   - V1.0 可以预留 write tool 接口，但默认不开放自动写入链路。
   - 不做自动提交 git、自动创建 PR、自动发布。

2. 不做完整多 Agent 团队系统
   - `CCLearning NO.5` 中的 teammate、mailbox、team protocol 可以作为后续方向。
   - V1.0 最多预留消息协议和任务委托接口，不实现完整自治团队。

3. 不做完整 MCP 生态
   - `CCLearning NO.6` 中 MCP 插件架构很重要，但 V1.0 不追求远程 MCP、OAuth、多传输类型、动态工具市场。
   - V1.0 可以设计 ToolSpec / ToolRegistry，使未来能接 MCP。

4. 不做复杂后台任务系统
   - `CCLearning NO.4` 中后台任务线程可以作为 V1.1+ 方向。
   - V1.0 不引入复杂并发、任务取消、长期后台 worker。

5. 不做完整技能系统
   - `CCLearning NO.2` 的按需技能加载可以先抽象为 prompt section 或 capability section。
   - V1.0 不做技能包安装、技能市场、复杂技能发现。

6. 不做图数据库或大型索引系统
   - V1.0 继续使用 JSON / Markdown 文件保存 index、graph、memory、tasks。
   - 不引入 Neo4j、向量数据库或外部服务作为必需依赖。

7. 不追求跨语言完整支持
   - 当前主线仍是 Python 项目。
   - V1.0 可以在架构上避免写死 Python，但验收目标仍以 Python 项目为主。

### 3.2 NO.1：最小 Agent 循环与权限门控

笔记要点：

- Agent 本质是一个循环：接收任务、决定工具、执行工具、观察结果、继续或停止。
- 工具定义需要同时给模型和 executor 使用。
- 权限与路径安全是 harness 的底层能力，不是工具内部的临时判断。
- 生产级实现需要 hook、policy、trace 共同参与。

映射到 PyCode：

- `agent/runtime.py`
  - 负责组织单次 Agent run。
  - 在 V1.0 中承担 `observe-decide-act` loop 主体。
  - 每一轮负责组装当前状态、请求 planner 决定下一步、调用 executor、观察结果、判断是否继续或停止。
  - 产出 `AgentResult`。

- `agent/planner.py` / `agent/llm_planner.py`
  - 当前主要负责从用户任务生成 steps。
  - V1.0 中升级为 next-action planner：根据当前上下文、已有 evidence、trace、todo 和工具结果决定下一步动作。
  - 规则 planner 作为离线兜底。
  - LLM planner 作为增强规划器。

- `agent/executor.py`
  - 负责执行 runtime 选中的单个 tool action。
  - 统一处理 `ToolCall`、`ToolResult`、错误和 evidence。

- `agent/policy.py`
  - 负责路径边界、工具权限、测试运行权限、危险操作拒绝。
  - 权限检查结果必须进入 trace。

- `tools/base.py`
  - 统一工具接口。
  - 明确 tool name、description、arguments schema、read only / destructive 标注。

V1.0 要做的 harness 内容：

- 把 runtime 从“一次性计划后顺序执行”升级为 `observe-decide-act` loop。
- 固化 Agent run / turn 状态机。
- 定义 next action 类型，例如 `tool_call`、`final_answer`、`ask_user`、`stop_with_error`。
- 固化 ToolSpec / ToolCall / ToolResult 数据结构。
- 补强 safe path 与权限拒绝事件。
- 建立工具注册表，避免 runtime 中硬编码工具映射无限膨胀。
- 让 trace 记录完整工具生命周期。

### 3.3 NO.2：TodoWrite、规划执行与技能加载

笔记要点：

- TodoWrite 解决复杂任务中的上下文漂移。
- 先规划后执行可以让 Agent 行为更可审查，但 V1.0 的主线不是停留在一次性计划，而是让 todo 服务每轮 loop 的进度管理。
- 子 Agent 解决上下文隔离，但不等于权限隔离。
- 技能加载解决 token 经济学问题。

映射到 PyCode：

- `agent/todo.py`
  - 保存本次 Agent run 的执行清单。
  - 三态：`pending`、`in_progress`、`completed`。
  - 同一时间最多一个 `in_progress`。

- `tools/todo_write.py`
  - 作为工具接口暴露 todo 更新能力。
  - 用于未来 LLM planner / LLM agent 主动维护任务进度。

- `agent/context.py`
  - 将 todo 摘要注入上下文。
  - 让最终回答能说明计划完成情况。

V1.0 要做的 harness 内容：

- 初始计划可以生成 todo，但 runtime 每轮也可以根据观察结果调整 todo。
- 工具执行前后自动更新 todo。
- 工具失败时 todo 保留失败信息或未完成状态。
- CLI / UI 展示 todo 进度。
- 预留 skill-like context section，但不做完整技能包系统。

V1.0 暂不做：

- 完整子 Agent。
- 自动技能发现与安装。
- 多层父子 Agent 递归调度。

### 3.4 NO.3：Memory、Prompt 组装与错误恢复

笔记要点：

- Memory 分为项目知识、工作流、分析结论、用户偏好等类型。
- Memory 不应该无差别注入，应该索引常驻、正文按需加载。
- 系统 prompt 应该由 section 组装，而不是硬编码大字符串。
- 错误恢复需要分类：模型错误、工具错误、权限错误、上下文错误。

映射到 PyCode：

- `agent/memory.py`
  - 负责 Markdown memory 文件和索引管理。
  - 支持 add / list / search / load。

- `tools/memory_tools.py`
  - 把 memory 操作暴露给 Agent。

- `agent/prompt_sections.py`
  - 定义身份、工具、权限、项目、证据、trace、todo、memory 等 section。

- `agent/context.py`
  - 负责按需选择、组装、截断和说明上下文来源。

- `llm_client.py`
  - 需要更明确地区分 API 配置错误、网络错误、模型返回错误、解析错误。

V1.0 要做的 harness 内容：

- Memory 类型和 frontmatter 固化。
- Memory 注入规则固化。
- Context section 输出可审查。
- Prompt 组装从字符串拼接升级为 section pipeline。
- 常见错误分类进入 `AgentResult` 和 trace。
- LLM 不可用时提供规则总结或明确降级输出。

### 3.5 NO.4：Task DAG 与长时任务基础设施

笔记要点：

- TodoWrite 管理单次运行内的扁平清单。
- Task DAG 管理跨会话、带依赖的任务。
- 后台任务解决长时间阻塞问题，但会带来生命周期、通知和取消复杂度。

映射到 PyCode：

- `agent/task_dag.py`
  - 保存 `.pclens/tasks/*.json`。
  - 支持 `create_task`、`list_tasks`、`get_task`、`claim_task`、`complete_task`。
  - 根据 `blocked_by` 判断任务是否可开始。

- `tools/task_tools.py`
  - 作为 Agent 工具暴露任务操作。

- `ui/streamlit_app.py`
  - 展示 Task DAG 当前状态。

V1.0 要做的 harness 内容：

- Task 数据模型稳定。
- Task 状态机稳定：`pending -> in_progress -> completed`。
- 依赖不存在时视为阻塞。
- `complete_task` 返回被解除阻塞的任务。
- CLI 能管理任务。
- Agent 能把跨会话计划写入 Task DAG。

V1.0 暂不做：

- 后台线程执行任务。
- 并发 claim 锁机制。
- 多 Agent 抢任务。
- 自动任务调度器。

### 3.6 NO.5：多 Agent 团队与通信协议

笔记要点：

- teammate 与 subagent 的区别是生命周期和自治程度。
- 文件邮箱可以作为跨进程、跨会话通信基础。
- 团队通信需要协议状态机，而不是随意发消息。
- 权限需要冒泡治理，不能让子系统绕过 lead 的安全边界。

映射到 PyCode：

- V1.0 当前没有完整对应模块。
- 可在设计上预留：
  - `agent/message_bus.py`
  - `agent/protocol.py`
  - `agent/team.py`
  - `agent/delegation.py`

V1.0 要做的 harness 内容：

- 不实现完整多 Agent。
- 在 Task DAG 和 ToolResult 中保留 `owner`、`source`、`run_id`、`parent_run_id` 等字段空间。
- 在文档中明确未来多 Agent 不得绕过 policy。
- 如果未来出现 subagent，也必须复用同一套 policy、trace、memory 注入规则。

V1.0 暂不做：

- teammate manager。
- mailbox 文件协议。
- agent idle loop。
- 权限冒泡实现。
- 自组织任务看板扫描。

### 3.7 NO.6：MCP、动态工具池与综合 Agent 合成

笔记要点：

- 手写工具会遇到扩展瓶颈，需要工具发现和动态组装。
- 动态工具池会影响 prompt 缓存和工具命名安全。
- 工具注解需要表达 readOnly / destructive 语义。
- MCP 涉及连接生命周期、配置优先级、传输、认证和错误恢复。

映射到 PyCode：

- `tools/base.py`
  - 作为 ToolSpec / ToolResult 的基础。

- 未来 `tools/registry.py`
  - 统一注册内置工具。
  - 输出给 planner / prompt / executor 使用。

- 未来 `integrations/mcp.py`
  - 预留 MCP 连接和工具发现。

V1.0 要做的 harness 内容：

- 统一 ToolRegistry。
- 每个工具标注：
  - name
  - description
  - argument schema
  - read_only
  - requires_confirmation
  - destructive
  - allowed_in_plan_only
  - output_summary_policy
- prompt 中的工具说明由 registry 生成。
- executor 调用工具也从 registry 查找。
- policy 根据工具注解做安全判断。

V1.0 暂不做：

- 真实 MCP client。
- 远程 server 连接。
- OAuth。
- 多传输类型。
- MCP 工具继承给子 Agent。

## 4. 当前已实现能力

根据当前 demo 版代码和文档，PyCode 已经具备以下基础能力。

### 4.1 代码结构理解

- 递归扫描 Python 文件。
- 忽略 `.git`、虚拟环境、缓存目录、`node_modules` 等。
- 使用 AST 提取 import、class、function、method。
- 生成 `.pclens/index.json`。
- 构建 `.pclens/code_graph.json`。
- 图谱包含 file、class、function、method 节点。
- 图谱包含 contains、imports、calls 等关系。
- 支持查询 imports、imported-by、calls、entry。

## 5. 缺口清单

### 5.1 Agent 主循环缺口

当前问题：

- 当前 runtime 更像计划执行器：planner 一次性生成 steps，executor 按顺序执行，最后汇总。
- 缺少每轮工具执行后的 observe -> decide continue/stop 机制。
- planner 的职责还偏“生成完整计划”，尚未升级为“当前状态下下一步该干什么”。
- runtime、planner、executor、context、summary 的边界需要围绕 loop 重新固化。
- Agent run / turn 状态机还不够明确。
- plan-only、rule-plan、LLM planner、normal run、loop run 的路径需要统一解释。

V1.0 需要补齐：

- 定义稳定的 `AgentRunState` 或等价状态结构。
- 定义稳定的 `AgentTurnState` 或等价状态结构。
- 明确 run lifecycle：
  - created
  - initializing
  - deciding
  - acting
  - observing
  - summarizing
  - completed
  - failed
  - cancelled / skipped
- 明确每轮 loop：
  - build current context
  - decide next action
  - policy check
  - execute action
  - observe result
  - update evidence / todo / trace / memory candidates
  - decide continue or stop
- 定义 next action 类型：
  - `tool_call`
  - `final_answer`
  - `ask_user`
  - `stop_with_error`
  - `no_op` / `skip`
- `AgentResult` 中稳定包含：
  - task
  - plan
  - turns
  - steps
  - tool_results
  - evidence
  - trace
  - todos
  - memories
  - context_sections
  - answer
  - errors
  - run_metadata

### 5.2 ToolRegistry 缺口

当前问题：

- 工具虽然已经模块化，但还需要更统一的注册、说明和权限元数据。
- prompt 中的工具说明、executor 的工具映射、policy 的工具权限判断应该来自同一个 registry。

V1.0 需要补齐：

- 新增或强化 `ToolSpec`。
- 新增 `ToolRegistry`。
- 每个工具声明：
  - name
  - description
  - input schema
  - output schema / output summary
  - read_only
  - destructive
  - requires_confirmation
  - allowed_in_plan_only
  - allowed_roots
  - timeout policy
- planner、executor、context builder 都从 registry 获取工具信息。

### 5.3 Policy 缺口

当前问题：

- 权限边界还需要更像 harness 层能力，而不是分散在工具内部。
- 对写文件、运行命令、测试命令、git 操作的策略需要更清楚。

V1.0 需要补齐：

- 统一路径安全检查。
- 统一工具权限检查。
- 权限拒绝进入 trace。
- 明确默认策略：
  - 读项目内文件：允许。
  - 搜索项目内代码：允许。
  - 查询 graph / index：允许。
  - 查看 git diff：允许。
  - 运行测试：需要显式参数。
  - 写文件：V1.0 默认不开放给 Agent 自动执行。
  - 删除文件、重置 git、提交 git：禁止。

### 5.4 Trace / Hook 缺口

当前问题：

- trace 已有基础，但需要确保每种工具结果、权限拒绝、异常恢复都能记录。
- hook 生命周期需要和 executor 更紧密对齐。

V1.0 需要补齐：

- 标准事件类型：
  - `user_prompt_submit`
  - `plan_created`
  - `pre_tool_use`
  - `policy_decision`
  - `post_tool_use`
  - `tool_error`
  - `context_assembled`
  - `llm_call_started`
  - `llm_call_finished`
  - `run_completed`
  - `run_failed`
- 每个事件包含：
  - run_id
  - timestamp
  - event_type
  - status
  - tool_name
  - args_summary
  - duration_ms
  - output_summary
  - error
  - evidence_refs

### 5.5 TodoWrite 缺口

当前问题：

- Todo 已经存在，但需要进一步保证它和计划步骤、工具执行之间的一致性。

V1.0 需要补齐：

- 每个 plan step 自动生成 todo。
- 执行 step 前 todo 进入 `in_progress`。
- 执行成功后 todo 进入 `completed`。
- 执行失败时 todo 保留失败原因。
- CLI / UI 展示 todo 进度和失败项。

### 5.6 Task DAG 缺口

当前问题：

- Task DAG 已有基础，但需要更明确地服务 V1.0 的跨会话任务恢复。

V1.0 需要补齐：

- 固化任务 schema。
- 增加 schema version。
- 任务文件读写异常处理。
- 依赖不存在、循环依赖、重复 task id 的处理。
- CLI 命令覆盖 create / list / get / claim / complete。
- Agent 可以把较大任务拆解并写入 Task DAG。

### 5.7 Memory 缺口

当前问题：

- Memory 已有基础，但注入规则、更新规则和过期风险需要更明确。

V1.0 需要补齐：

- Memory 类型：
  - project
  - workflow
  - analysis
  - preference
  - limitation
- Memory frontmatter：
  - id
  - type
  - title
  - created_at
  - updated_at
  - source
  - confidence
  - related_files
- 注入策略：
  - MEMORY index 可摘要注入。
  - 正文只按任务相关性注入。
  - 过期或低置信度 memory 需要标注。
- Agent 不默认把所有对话写入 memory。

### 5.8 Context Builder 缺口

当前问题：

- Context section 已有基础，但 V1.0 需要让它成为 prompt 的唯一组装入口。
- loop 化之后，context builder 需要支持“每一轮当前状态”的组装，而不只是最终总结前的一次组装。

V1.0 需要补齐：

- 统一 section 类型：
  - identity
  - tools
  - policy
  - project
  - retrieval
  - evidence
  - trace
  - todo
  - tasks
  - memory
  - user_task
  - response_contract
- 每个 section 有：
  - name
  - source
  - priority
  - content
  - token_estimate 或 size estimate
  - included / skipped reason
- 支持输出 context debug 视图。
- 支持按 turn 输出 context 摘要，说明 planner 每次决定下一步时看到了什么。

### 5.9 LLM Planner / LLM Client 缺口

当前问题：

- LLM planner 与规则 planner 的边界需要更清楚。
- LLM 输出解析失败时需要可恢复。
- planner 需要从“一次性完整计划输出”扩展到“next action 输出”。
- V1.0-A 已经建立规则版 next-action loop，但每一轮“下一步做什么 / 是否停止 / 是否 final answer”还不是 LLM 决定。
- 当前最终结果总结在提供 `llm_client` 时仍由 LLM 根据 summary context 生成；未提供 LLM 时只返回结构化结果、trace、context 和 prompt。

V1.0 需要补齐：

- LLM planner 输出 schema 校验。
- schema 解析失败时回退规则 planner。
- 定义 next-action planner 输出 schema。
- 支持 planner 基于当前 evidence、trace、todo、tool results 判断下一步动作。
- 支持 planner 明确输出停止条件和最终回答草案。
- 在 V1.0-C 中将 loop 的核心决策从规则 next-action planner 升级为 LLM next-action planner。
- V1.0-C 必须让 LLM 能输出结构化 action，而不是只输出自然语言总结。
- LLM client 错误分类：
  - missing config
  - auth failed
  - rate limited
  - timeout
  - invalid response
  - schema parse failed
- 所有 LLM 错误进入 trace。

### 5.10 Demo 到 V1.0 工程化缺口

当前问题：

- README 和 demo 已经能展示，但 V1.0 需要更稳定的验收标准。

V1.0 需要补齐：

- V1.0 测试清单。
- V1.0 demo script。
- V1.0 技术说明。
- V1.0 版本边界。
- 真实示例任务输出。
- 失败场景示例。

## 6. 优先级

## 7. 风险边界

### 7.1 产品定位风险

风险：

- 如果 V1.0 追求完整 Claude Code / Codex 形态，项目会失去自己的主线。
- PyCode 的核心价值是“代码库理解与开发分析”，不是“通用 Agent 平台”。

边界：

- 所有 harness 能力都必须服务于代码理解、影响分析、证据追踪。
- 如果某个功能不能改善这些场景，就不进入 V1.0 主线。

### 7.2 功能膨胀风险

风险：

- 多 Agent、MCP、后台任务、技能系统都很吸引人，但会显著增加复杂度。
- 如果同时做，V1.0 会变成很多半成品。

边界：

- P0 优先稳定单 Agent harness。
- P1 再增强记忆、任务和验收场景。
- P2 只做接口预留。
- P3 不做。

### 7.3 安全风险

风险：

- Agent 工具一旦具备写文件、运行命令、git 操作能力，就可能破坏项目。
- 权限判断散落在工具内部会变得不可审查。

边界：

- 默认只读。
- 默认不自动修改代码。
- 默认不自动提交 git。
- 默认不运行测试，除非显式开启。
- 危险命令禁止。
- 所有拒绝进入 trace。

### 7.4 上下文污染风险

风险：

- Memory、trace、todo、tasks、retrieval 全部注入 prompt 会造成噪声和 token 浪费。
- 过期 memory 可能覆盖当前代码事实。

边界：

- Context Builder 统一注入。
- 每个 section 必须有来源和 included / skipped reason。
- Memory 正文按需注入。
- 当前代码事实优先于历史 memory。

### 7.5 LLM 不稳定风险

风险：

- LLM planner 可能输出非法 schema。
- LLM 总结可能脱离 evidence。
- API 不可用会破坏 demo。

边界：

- 规则 planner 永远作为兜底。
- LLM 输出必须校验。
- LLM 错误进入 trace。
- `plan-only --rule-plan` 作为离线稳定演示路径。
- 最终回答必须尽量引用 evidence。

### 7.6 工程复杂度风险

风险：

- ToolRegistry、Policy、Trace、Context、Memory、Task DAG 如果互相交叉引用，会造成架构混乱。

边界：

- ToolRegistry 只描述工具。
- Policy 只做权限决策。
- Executor 只执行工具并收集结果。
- Trace 只记录事件。
- Context Builder 只组装上下文。
- Runtime 只编排流程。
- Memory / Task DAG 是状态存储，不直接决定工具执行。

### 7.7 展示与真实能力不一致风险

风险：

- Demo UI 很容易展示得比实际能力更强。
- 面试或 README 中如果没有边界说明，会显得不可信。

边界：

- README 明确当前局限。
- UI 展示 trace / evidence / context，而不是只展示漂亮回答。
- 示例问题选择真实可运行场景。
- 不声称支持自动修复、完整代码生成或跨语言全覆盖。

## 9. V1.0 验收标准

V1.0 完成时，至少需要满足：

1. runtime 不再只是顺序执行预生成 steps，而是至少支持一条 observe -> decide next action -> continue/stop 的 loop 路径。
2. planner 能基于当前状态输出下一步动作，而不只输出完整计划列表。
3. V1.0-C 完成后，LLM planner 能参与每轮 next-action 决策，而不是只生成初始计划或最终总结。
4. 运行离线演示命令时，不依赖 LLM 也能展示 loop turns、todo、trace、context。
5. 运行普通 Agent 任务时，工具调用均经过 policy 和 trace。
6. 权限拒绝不会崩溃，并能在结果中解释。
7. LLM 不可用时有明确降级。
8. Memory 不会无差别污染上下文。
9. Task DAG 可以跨会话保存和查询。
10. CLI 和 UI 能展示 Agent 每一轮看到了什么、决定了什么、调用了什么、依据来自哪里。
11. README 能说明 V1.0 的能力、边界和后续方向。
12. 测试覆盖 P0 模块的关键路径。
13. 项目负责人可以清楚讲出：
    - 为什么需要自己的 harness。
    - 为什么 V1.0 要从 `plan-and-execute` 走向 `observe-decide-act` loop。
    - 为什么 V1.0-A 是规则 loop，而 V1.0-C 才完善 LLM-driven loop。
    - PyCode 和普通聊天式代码问答的区别。
    - 为什么 V1.0 暂不做完整多 Agent / MCP。

## 10. 总结

V1.0 的关键词是：

```text
observe-decide-act loop、next-action planner、统一工具注册、权限门控、可观测 trace、可审查 context、可恢复 memory/task、可解释 evidence。
```

`CCLearning NO.1-6` 提供的是成熟 Agent harness 的能力地图。PyCode V1.0 不应该照搬所有机制，而应该吸收其中最能服务当前项目目标的部分：`observe-decide-act` 单 Agent 主循环、next-action planner、工具生命周期、权限策略、Todo、Trace、Memory、Task DAG、Context Builder 和错误恢复。

多 Agent、MCP、后台任务和完整技能系统是重要方向，但更适合建立在 V1.0 稳定 harness 之上。V1.0 的成功标准不是“看起来像 Claude Code”，而是“PyCode 自己的 Agent 内核已经足够清楚、稳定、可信，并能支撑后续继续演进”。
